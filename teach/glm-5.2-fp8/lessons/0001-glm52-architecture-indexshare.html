Part 0：一句话定位

你已经掌握 MLA、MoE sigmoid routing、以及 DeepSeek-V3.2 的 DSA（lightning indexer 选 top-k token → sparse MLA）。GLM-5.2 在算法层面不是一个新范式，它 = DeepSeek-V3.2 风格的 MLA + DSA，外加三个增量：

增量是什么本课重点
IndexShareDSA 的 index 不再每层重算，而是每 4 层算一次、中间 3 层复用★ 主角
1M 原生 contextrope_theta=8M，非 YaRN/NTK 外推顺带
改进版 MTP单 nextn 层，acceptance length +20%，且MTP 迭代复用同一份 index课 02 细讲
定位锚点：DSA 解决"单层内 attention 是 O(n²)"——选 top-2048。IndexShare 解决"每层都要重新选一次 top-2048 也很贵"——既然相邻层选出来的 token 高度重合，那就别每层都选。一句话：DSA 压缩"算哪些 token"，IndexShare 压缩"多久选一次 token"。

架构标识：model_type = glm_moe_dsa，architectures = ["GlmMoeDsaForCausalLM"]。主读物 → arXiv:2603.12201 IndexCache: Accelerating Sparse Attention via Cross-Layer Index Reuse（本课所有 IndexShare claim 的一手来源）。

Part 2：IndexShare —— 本课主角

2.1 机制：每 4 层算一次 index

DSA 每一层都要跑一遍 indexer：投影 → MQA logits → topk，为该层的 query 选出 top-2048 个 key。IndexShare 的观察是：相邻层选出来的 top-2048 集合高度重合，因为它们读的是同一条残差流、语义在层间平滑变化。既然重合，就没必要每层重选。

config 用两个旋钮控制：index_topk_freq = 4（每 4 层重算一次）、indexer_types 标记每层是 full（重算）还是 shared（复用）。78 层的"重算层"落点是：

所以一个 4 层周期里，indexer 只跑 1 次而非 4 次 → indexer 部分省 ~4×。注意前缀 layer 0,1,2 是 dense MLP 层且每层都算 full index（浅层语义变化快，不敢复用），从 layer 3 才进入"周期复用"。

2.2 为什么安全：index 在层间变化缓慢

核心论证（arXiv:2603.12201）：把"第 L 层为某 query 选出的 top-2048 集合"记作 SL。实测 |SL ∩ SL+1| / 2048 接近 1——相邻层的选择几乎一样。用 SL 去近似 SL+1、SL+2、SL+3 的误差很小，而省下的是整整 3 层的 indexer 计算。这是一个用极小质量损失换大量计算的 Pareto 改进。

关键区分：IndexShare 复用的是"选哪些 token"（index），不是"attention 的输出"。每一层仍然用自己的 Q/K/V、自己的 SparseMLAOp 做完整 attention——只是在哪些 token 上做这件事，沿用了上游层的决定。所以表达能力几乎不受损：每层的 attention 权重仍是该层独立学出来的。

2.3 收益与 tradeoff

维度结论
FLOPs 节省1M context 下 per-token 2.9×（indexer 调用频率降到 1/4，且省去重复的 logits/topk）
质量损失近乎为零（相邻层 index 重合度高）
freq 的选择太大（如每 8 层）→ 远层语义漂移、index 失配掉点；太小（每 2 层）→ 省得少。4 是工程甜点
额外收益index_share_for_mtp_iteration=true：MTP draft 迭代直接复用 base 的 index，speculative decoding 不必为草稿 token 重选
易错点：IndexShare ≠ KV cache 共享，也 ≠ attention 输出共享（那是 cross-layer attention / YOCO 那一类）。它只共享稀疏选择的 index 张量。KV cache 仍是 MLA 压缩的 per-layer latent；attention 仍 per-layer 计算。把这三者搞混是最常见的理解错误。

Part 3：三方对比 —— 稀疏注意力的"层间"新轴

你在 minimax-m3 workspace 学过 NSA / DSA / MSA 的对比，那是"单层内"怎么选 token 的对比轴。IndexShare 引入了一条正交的新轴：跨层多久重选一次。把两条轴放一起：

方法单层内 indexer 粒度跨层 index 频率KV 形态
DeepSeek-V3.2 DSAtoken-level，lightning indexer每层重算MLA 压缩 latent
MiniMax-M3 MSAblock-level，per-group selection每层重算full KV（稀疏计算）
GLM-5.2 IndexSharetoken-level（同 DSA）每 4 层重算MLA 压缩 latent
关键洞察：IndexShare 不和 DSA/MSA 竞争"怎么选 token"——它站在 DSA 之上，正交地砍掉"选 token"这个动作本身的频率。理论上 IndexShare 这层复用思想也能叠加到 MSA 上（MSA 的 block selection 同样在相邻层重合）。这就是为什么把它理解成"DSA 的一个工程优化层"而非"新的 attention 算法"才准确。

与 DeepSeek-V3.2 的具体差异（一句话版）

同样的 MLA 维度家族（kv_lora=512、qk_rope=64）、同样的 lightning indexer（FP8 + deep_gemm MQA logits + topk_transform）、同样的 256/8/1 MoE——唯一的算法增量就是 indexer 的跨层复用，加上把 context 拉到 1M。这也解释了课 02 的核心结论：day-0 适配能大量复用 DeepSeek-V3.2 的代码路径。

Part 4：检索练习

先合上上面的内容，凭记忆作答，再展开核对。这是 storage strength 的关键——effortful retrieval。

Q1. IndexShare 在相邻层之间复用的，到底是哪一个张量？

复用的是 index（稀疏选择出的 top-2048 key 位置）。不是 KV cache，不是 attention 输出，不是 Q/K/V。每层仍用各自的权重做完整 SparseMLA attention，只是"在哪些 token 上做"沿用上游层。

Q2. 为什么跨层复用 index 几乎不掉点？用一句话回答其依据。

因为相邻层为同一 query 选出的 top-2048 集合高度重合（残差流语义在层间平滑变化），用上游 index 近似下游层误差极小（arXiv:2603.12201 实测）。

Q3. index_topk_freq=4 偏大或偏小分别会怎样？各一句。

偏大（如 8）：远层语义已漂移，复用的 index 失配，质量下降。偏小（如 2）：重选太频繁，省下的计算变少。4 是质量与计算的工程甜点。

Q4. 用一句话区分 DSA 与 IndexShare 各自压缩了什么。

DSA 压缩"对哪些 token 算 attention"（每 query 选 top-2048）；IndexShare 压缩"多久重新选一次 token"（每 4 层选一次）。两条轴正交。

Q5. GLM-5.2 相对 DeepSeek-V3.2，唯一的注意力算法增量是什么？

indexer 的跨层索引复用（IndexShare）。MLA 维度、lightning indexer、MoE 配置基本一致；其余差异是 1M context 与改进版 MTP。
