Part 0：重要前提 —— 上游已经做完了

你最初的问题是"GLM-5.2 怎么 day-0 支持？有什么 tricks？"。在社区上游 SGLang 里，答案不是一份"待办清单"，而是一份已合入的真实实现——而且它优雅到值得当成 case study：支持一个全新 frontier 模型，几乎没有写新代码。

你以为要做的上游实际的做法
写一个 glm_moe_dsa.py 模型文件3 行子类塞进 glm4_moe.py 末尾
实现 MLA + DSA + indexer全部继承 DeepseekV2ForCausalLM
给新架构加一堆 if glm: ... 分支零架构分支——靠能力探测 is_deepseek_dsa()
从零写 IndexShare已在 DeepSeek DSA 通用代码里，GLM 只是开了 index_topk_freq
本课的总纲：SGLang 接 GLM-5.2 用的是一种"能力驱动（capability-driven）"而非"身份驱动（identity-driven）"的设计。框架不问"你是不是 GLM"，而问"你的 config 里有没有 index_topk"——有就走 DSA 稀疏路径。所以一个新模型只要声明能力（config 字段对、架构名进几个白名单 set），就自动复用整条 DSA 流水线。这就是 day-0 能"零新文件"的根本原因，也是你能从这份实现里偷走的最大架构智慧。

对照：百度 aiak_sglang fork 在我第一次检索时 GlmMoeDsa/index_share 全零匹配——说明 fork 落后于上游。要让 fork 支持 GLM-5.2，最佳路径不是手写，而是把上游这套 cherry-pick 回来。本课拆的就是"要 pick 什么"。

1.1 关键开关：is_deepseek_dsa() 检查的是"能力"

整套 DSA 行为不是被"架构名 == GLM"打开的，而是被一个能力探测函数打开的：

configs/model_config.py:103
def is_deepseek_dsa(config) -> bool:
    return (
        _hf_arch(config) in (
            "DeepseekV3ForCausalLM", "DeepseekV32ForCausalLM",
            "DeepseekV3ForCausalLMNextN", "MistralLarge3ForCausalLM",
            "PixtralForConditionalGeneration",
            "GlmMoeDsaForCausalLM",          # ← GLM 只是名单里多一行
        )
        and _hf_attr(config, "index_topk") is not None   # ← 真正的能力判据
    )
读这段的正确姿势：架构名白名单是"允许进门"，index_topk is not None 才是"是不是 DSA"的实质判据。一个模型只要 config 里有 index_topk 且名字进了这个 set，就自动获得：Indexer 模块实例化、use_dsa=True、dsa 后端、稀疏注意力——全是 DeepSeek-V3.2 已经写好的通用代码。GLM 的"接入"本质上就是往这个 set 加一个字符串。

注意一个上游近期的重命名（对照你在 minimax workspace 学的"nsa backend"，名字变了）：

Part 2：3 行模型类 + HF config 修补 trick

2.1 整个模型类只有 3 行

models/glm4_moe.py:1481
class GlmMoeDsaForCausalLM(DeepseekV2ForCausalLM):
    def determine_num_fused_shared_experts(self):
        super().determine_num_fused_shared_experts("GlmMoeDsaForCausalLM")

EntryClass = [Glm4MoeForCausalLM, GlmMoeDsaForCausalLM]   # 1486

它继承 DeepseekV2ForCausalLM，不覆盖任何 forward——MLA、Indexer、SparseMLA、MoE、权重加载全部白嫖。唯一覆盖的 determine_num_fused_shared_experts 是为了把自己的架构名传进 DeepSeek 那个"shared expert 融合"的硬检查里（deepseek_v2.py 检查 architectures[0] != architecture or n_routed_experts != 256 or n_shared_experts != 1）。GLM-5.2 是 256/1，数值过关，融合保持开启。

Trick A：用"显式传名"绕过架构硬检查。 框架里残留的 architectures[0] == "DeepseekV3..." 这类身份判断，不去改它的 list，而是子类把自己的名字当参数传进去让检查通过。这是把"身份驱动"的旧代码温和地适配到新模型的标准手法。

2.2 HF config 修补：一个真实的兼容性 trick

这是最容易被忽略、却必须做的一步。HF transformers 的 GlmMoeDsaConfig 类在解析时会丢掉 DSA 路径需要的字段，SGLang 只能从原始 config.json 重新读回来：

utils/hf_transformers/config.py:70
if config.architectures[0] == "GlmMoeDsaForCausalLM":
    # GlmMoeDsaConfig drops/clobbers raw checkpoint fields the DSA path
    # needs, so re-read them from config.json and restore.
    raw_config, _ = PretrainedConfig.get_config_dict(model, revision=revision)
    for key in ("qk_rope_head_dim", "index_topk_freq"):
        if key in raw_config:
            setattr(config, key, raw_config[key])
    if hasattr(config, "qk_head_dim") and hasattr(config, "qk_nope_head_dim"):
        config.qk_head_dim = config.qk_nope_head_dim + config.qk_rope_head_dim
为什么这是 day-0 的隐形地雷：被丢掉的两个字段恰恰是命脉——qk_rope_head_dim（MLA 的 rope 维度，错了 attention 直接崩）和 index_topk_freq（IndexShare 的周期，丢了就退化成每层重算、白白损失 2.9×）。注释里还写明这是 transformers 的 bug（已由 HF PR #46338 上游修复），等 SGLang 依赖 transformers≥5.10 就能删掉这段。教训：day-0 适配里，"HF config 解析层的字段丢失"和"模型 forward 写错"一样致命，但前者更隐蔽。

Part 3：IndexShare 在代码里长什么样（本课核心）

课 01 讲了 IndexShare 的算法："每 4 层重算一次 index，中间复用"。现在看它在 SGLang 里物理上怎么实现。一句话剧透：没有任何全局 cache 对象——共享的 index 就是一个张量，沿着层循环用函数参数一层层往下传。

3.1 每层在 __init__ 时算好两个布尔：skip_topk / next_skip_topk

deepseek_v2.py:1604  (index_topk_freq 默认模式)
self.skip_topk      = max(layer_id - 1, 0) % self.index_topk_freq != 0
self.next_skip_topk = layer_id % self.index_topk_freq != 0

# 或 offset 模式 (1617): 让"重算层"对齐到 checkpoint 实际带权重的层
self.skip_topk = max(layer_id - index_skip_topk_offset + 1, 0) % freq != 0
  • skip_topk=True → 本层不跑 indexer，复用上一层传来的 index。
  • next_skip_topk=True → 把本层的 index 返回给下一层用。
把算法和真实权重对上：GLM-5.2 的 checkpoint 只在层 [0,1,2, 6,10,14,18,...] 带 indexer 权重（见课 01 / 权重校验）。代入 offset 模式、freq=4, offset=3：
  L=0,1,2 → skip_topk=False（dense 前缀，每层自算）
  L=3,4,5 → True（复用 L2） |  L=6 → False（重算） |  L=7,8,9 → True …
正好复现 [0,1,2,6,10,14,...]。关键洞察：skip_topk 的层在 checkpoint 里根本没有 indexer 权重（forward_mla.py:253 注释明说"shared layers carry no indexer weights"）。所以复用不是"省着算"的优化选项，而是结构性强制——没权重可算，只能复用。

3.2 层内的门控：算 or 复用

deepseek_common/attention_forward_methods/forward_mla.py:261

else:
    # 复用上一层传来的 index
    topk_indices = maybe_capture_indexer_topk(self.layer_id, prev_topk_indices)
...
# 函数末尾 (748): 决定要不要把 index 传给下一层

if not self.next_skip_topk:       return output, None          # 下层自己算

这里藏着一个真实的 correctness trick（直接回答你的"有什么坑？"）：注释 forward_mla.py:253-260 警告——千万不要把门控条件放宽成 or prev_topk_indices is None。因为 skip_topk 层没有 indexer 权重，一旦 cross-layer 传递断了（比如 TBO 双批重叠路径会丢掉 topk_indices），fallback 去"自己算"就会用未初始化的 indexer 产生垃圾 index，导致选出 >index_topk 的乱序 token。唯一允许 fallback 的是 MTP 层（layer 78 有自己的权重）。这是"index 跨层传递"实现里最容易踩的隐性 bug。

3.3 谁来串起来：model.forward 的层循环持有那个张量

deepseek_v2.py:2477   topk_indices = None        # 循环外初始化
deepseek_v2.py:2495   for i in ...:
    hidden_states, residual, topk_indices = layer(
        ..., prev_topk_indices=topk_indices,    # 上一轮的结果当这一轮的输入
    )

就这么简单：一个普通的 Python 变量 topk_indices，在层循环里被反复读写。"重算层"把它刷新成新 index；"复用层"原样透传。没有 KV-pool 那种持久 buffer，没有全局 IndexCache 单例——共享的状态就活在这个循环变量里，生命周期 = 一次 forward。

对比你预期的实现：在我重写本课前，基于 fork（没有 IndexShare）的推测是"需要一个 per-forward-batch 的 IndexCache 缓存对象"。上游的真实做法更轻——根本不需要缓存容器，用层间函数参数传递就够了，因为层是顺序执行的，天然形成一条传递链。这是个很好的"不要过度设计"案例：能用调用栈传递的状态，就别建全局 cache。

                            if forward_batch.reuse_mtp_topk_indices else None))

流程：第 1 个 draft step 时 topk_indices=None → MTP 层（is_nextn 使 skip_topk=True 但允许"无传入时自算"的 fallback）算出一份 index 并写回 forward_batch.topk_indices；后续 step 直接复用这份，不再重算。所有 step 跑完后清场（eagle_worker_v2.py:625 把两个字段还原）。

又一个 correctness 约束（直接的 trick）：复用只在 self.topk == 1 时启用。注释 eagle_worker_v2.py:191 说明原因——select_top_k_tokens 在 topk>1 时会重排 row 顺序，导致复用的 index 与当前 token 行错位（desync）。这是"时间复用"特有的坑：空间复用里层不会重排 token，时间复用里 speculative 的 tree 展开会。同样是复用 index，两条通道的失效模式完全不同——这正是值得你深挖的地方。

Part 6：检索练习

合上页面凭记忆作答，再展开核对。

Q1. 上游 SGLang 判断"这个模型要不要走 DSA 稀疏路径"，靠的是什么？答出实质判据。

靠能力探测 is_deepseek_dsa()：架构名进白名单 set 且 config.index_topk is not None。是"有没有这个能力字段"，不是"是不是叫 GLM"。

Q2. GlmMoeDsaForCausalLM 模型类自己写了多少计算逻辑？为什么能这么少？

几乎没有：3 行子类继承 DeepseekV2ForCausalLM，只覆盖共享专家融合的传名。因为 MLA+DSA+MoE 全是 DeepSeek 通用代码，GLM 只需声明能力即可复用。

Q3. IndexShare 跨层共享的 index，物理上存在哪里？不是什么？

存在 model.forward 层循环的局部变量 topk_indices 里，靠 prev_topk_indices 参数一层层传。不是全局 cache、不是持久 KV buffer——生命周期就一次 forward。

Q4. 为什么 shared 层不能在 prev_topk_indices 为 None 时 fallback 去自己算 index？

因为 skip_topk 层的 checkpoint 根本不带 indexer 权重，自己算会用未初始化 indexer 产出乱序 index（选出 >index_topk 的垃圾）。仅 MTP 层有自己权重可 fallback。

Q5. 层间复用与 MTP 迭代复用，载体分别是什么？为什么不同？

层间用循环局部变量（层顺序执行，调用栈串得起来）；MTP 用 forward_batch.topk_indices 字段（每 draft step 是独立 forward，局部变量活不过去，必须挂 batch）。

Q6. index_share_for_mtp_iteration 为什么限定 topk==1？

因为 select_top_k_tokens 在 topk>1 时会重排 row 顺序，复用的 index 会与当前 token 行错位（desync）。这是时间复用特有的失效模式。

Q7. config.py:70 那段"重读 config.json"的 trick 抢救了哪两个字段？丢了各有什么后果？

抢救 qk_rope_head_dim（丢了 MLA rope 维度错、attention 崩）和 index_topk_freq（丢了 IndexShare 退化成每层重算、损失 2.9× 加速）。HF Config 类会 clobber 它们。
