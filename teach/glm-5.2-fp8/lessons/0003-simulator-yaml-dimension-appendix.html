Part 0：结论先行

疑问短答案如果不改会怎样
head_dim 为啥写这么细GLM-5.2 同时有 qk_nope=192、qk_rope=64、qk=256、v=256、kv_latent=576、sparse_mla=576。一个字段装不下这些语义。CP all-gather、SparseMLA DB shape、q_b/kv_b/o_proj 的 GEMM 维度会互相污染。
indexer_k_norm 为啥是 LayerNorm权重里有 k_norm.weight + k_norm.bias；SGLang 代码直接实例化 LayerNorm。RMSNorm 没 mean subtraction、通常无 bias，数值语义和 profiler IO 都错。
MTP 为啥两个 norm + 一个大 GEMMSGLang NextN 先分别 normalize draft embed 与 target hidden，再 concat 成 2H，用单个 eh_proj: 2H → H 融合。拆成 e_proj/h_proj 会漏两个 norm、漏 concat 语义、漏真实 GEMM shape，decode 路径还会少 speculative draft 开销。
一句话原则：simulator YAML 是性能模型的形状契约。凡是被不同算子消费的维度，必须用不同字段表达；否则 parsed/query 能过，result 和 profiler 语义仍可能错。

Part 1：head_dim 为什么要拆清楚

GLM-5.2 和 DeepSeek V3.2 属于同一类 MLA/DSA 结构，都会把 Q/K 拆成 no-RoPE 部分和 RoPE 部分，也都会把 KV cache 存成 latent cache。问题不在模型思想差异，而在 head_dim 这个名字在不同代码层表达的不是同一个东西。

1.1 GLM-5.2 里至少有 5 个 head-like 维度

字段值来源/公式消费者
head_dim192HF config 字段；等价于 qk_nope_head_dim不要拿它当通用 head dim
qk_rope_head_dim64HF configmain RoPE、indexer RoPE
qk_head_dim256192 + 64q_b_proj 输出：64 * 256
v_head_dim256HF configo_proj 输入：64 * 256
kv_latent_cache_dim576kv_lora_rank 512 + rope 64CP KV cache all-gather/rerange
sparse_mla_head_dim576nope 192 + v 256 + rope 64DSA SparseMLA kernel query shape

1.2 为什么之前不区分，现在必须区分

老 YAML 里 head_dim=256 被当作 v_head_dim alias 使用；局部看没问题，因为 qk_head_dim 和 v_head_dim 恰好都等于 256。但同一个字段后来被 CP 策略拿去当 KV cache all-gather 的 hidden size。这个 hidden size 真实值是 512+64=576，不是 256，更不是 HF 的 192。

deepseek_v2.py:1943-1955
latent_cache[..., : self.kv_lora_rank] = k_nope.squeeze(1)
latent_cache[..., self.kv_lora_rank :] = k_pe.squeeze(1)
latent_cache_output = cp_all_gather_rerange_output(...)
k_nope = latent_cache_output[..., : self.kv_lora_rank]
k_pe = latent_cache_output[..., self.kv_lora_rank :]

这段说明 CP all-gather 的对象是 latent cache：前半段 kv_lora_rank，后半段 qk_rope_head_dim。GLM-5.2 是 512 + 64 = 576。

反证法：如果继续用一个 head_dim，它要同时等于 192、256、576。只有两种结果：要么策略代码靠上下文猜含义，要么某条路径静默错形状。两者都比显式字段更危险。

1.3 与 DeepSeek V3.2 的关系

GLM-5.2 和 DS V3.2 的结构确实相近：都是 DeepSeek-style MLA + DSA/Indexer，SGLang 也让 GLM 继承 DeepseekV2ForCausalLM。但这只说明公式相近，不说明某个叫 head_dim 的字段可被全局复用。

正确类比：DS V3.2 和 GLM-5.2 都需要分清 qk_nope、qk_rope、v_head、kv_latent。如果旧 simulator 没分清，只是旧债没暴露；不是 GLM-5.2 可以继续混用的理由。

Part 2：indexer_k_norm 为什么是 LayerNorm

2.1 权重证据：它有 bias

HF safetensors index 里，full-indexer 层存在：

model.layers.0.self_attn.indexer.k_norm.weight
model.layers.0.self_attn.indexer.k_norm.bias

shared-indexer 层，例如 layer 3，没有 indexer k_norm tensors。这个分布与 SGLang 的 skip_topk 逻辑一致：full 层有 indexer 权重，shared 层复用前一层 topk。

bias 是关键物证：RMSNorm 只按均方根缩放，通常只有 weight；LayerNorm 是减均值、除标准差、再乘 weight 加 bias。出现 k_norm.bias，就不能把它建模成 RMSNorm。

2.2 代码证据：SGLang 明确实例化 LayerNorm

dsa_indexer.py:368-370
self.k_norm = LayerNorm(
    self.head_dim, dtype=torch.bfloat16 if _use_aiter else torch.float32
)

随后 key 路径是：

dsa_indexer.py:479-485
key, _ = self.wk(x)
key = self.k_norm(key)
k_rope, _ = torch.split(key, [self.rope_head_dim, self.head_dim - self.rope_head_dim], dim=-1)
q_rope, k_rope = self.rotary_emb(positions, q_rope, k_rope)

注意这里 q_lora 已经在主 MLA 路径里经过 q_a_layernorm，但 indexer 的 wq_b 之后没有 q_b_norm。我们补的是 key 侧的 k_norm，不是凭空给 q_b 加 norm。

Part 3：MTP 为什么是两个 norm + 一个大 GEMM

3.1 权重名字已经给出结构

HF 权重 index 的 MTP 特殊张量是：

model.layers.78.enorm.weight
model.layers.78.hnorm.weight
model.layers.78.eh_proj.weight
model.layers.78.shared_head.norm.weight

这不是 e_proj.weight + h_proj.weight，而是两个 norm + 一个 eh_proj。名字已经说明它先处理 e 和 h，再用一个投影融合。

3.2 SGLang 代码：draft model 被改写成 NextN

model_config.py:421-426
if is_draft_model and self.hf_config.architectures[0] in [
    'DeepseekV3ForCausalLM', 'DeepseekV32ForCausalLM', 'GlmMoeDsaForCausalLM',
]:
    self.hf_config.architectures[0] = 'DeepseekV3ForCausalLMNextN'

GLM-5.2 的 speculative draft 层直接复用 DeepSeek NextN 实现。NextN 初始化：

deepseek_nextn.py:106-120
self.enorm = RMSNorm(config.hidden_size, eps=config.rms_norm_eps)
self.hnorm = RMSNorm(config.hidden_size, eps=config.rms_norm_eps)
self.eh_proj = nn.Linear(2 * config.hidden_size, config.hidden_size, bias=False)

NextN forward：

deepseek_nextn.py:201-218
eh_input = torch.cat(
    (self.enorm(hidden_states), self.hnorm(forward_batch.spec_info.hidden_states)),
    dim=-1,
)
hidden_states = self.eh_proj(eh_input)

3.3 为什么不是两个小 GEMM

在线性代数上，单个 [H, 2H] 矩阵可以切成左右两半，看起来像 W_e e + W_h h。但 simulator 不能只看代数等价，还要匹配真实实现的 kernel shape 和前后算子。

角度单个 eh_proj两个 e_proj/h_proj
权重命名匹配 eh_proj.weight权重里无这两个名字
前处理显式建模 enorm/hnorm旧 YAML 漏掉两个 norm
GEMM shapem x 6144 x 12288两个 m x 6144 x 6144，DB/profiler shape 不同
实现路径符合 SGLang forward需要额外 add/mix，旧 YAML 没有表达
关键边界：如果某个后端真实把 eh_proj 拆成两个 GEMM 并显式 add，那 simulator 可以按真实后端拆。但 SGLang 社区代码不是这样写的；当前 YAML 应先对齐真实模型路径。

3.4 为什么 decode 也要保留 MTP

MTP 的主要用途就是 speculative decoding。SGLang 在 NextN decoder 里还把 topk indices 复用接进来：

deepseek_nextn.py:227-240
hidden_states, residual, topk_indices = self.decoder(
    ...,
    prev_topk_indices=(forward_batch.topk_indices if forward_batch.reuse_mtp_topk_indices else None),
)
if forward_batch.reuse_mtp_topk_indices:
    forward_batch.topk_indices = topk_indices

所以 decode 时删除 mtp_proj 会刚好删掉 speculative draft 的入口开销。这不是优化，是路径缺失。

Part 5：自测题

Q1. 为什么 head_dim=256 在 GLM-5.2 YAML 里危险？

因为 256 只能表示 qk_head_dim 或 v_head_dim，不能表示 HF 的 head_dim=192，也不能表示 CP KV cache 的 576。字段名一旦被策略代码复用，就会错形状。

Q2. 判断 indexer_k_norm 是 LayerNorm 的最短证据链是什么？

权重 index 有 indexer.k_norm.bias；SGLang 代码有 self.k_norm = LayerNorm(...)；forward 中 key = self.k_norm(key) 后再 split rope 并 apply RoPE。

Q3. MTP 的两个 norm 分别归一化什么？

enorm 归一化 draft/input embedding 侧的 hidden_states；hnorm 归一化 target model 传来的 forward_batch.spec_info.hidden_states。两者 concat 后进 eh_proj。

Q4. 两个 6144x6144 GEMM 在数学上看似可行，为什么 simulator 仍改成一个 6144x12288 GEMM？

因为 simulator 要对齐真实 kernel shape、权重命名、quant/profiler 数据和 forward 路径。SGLang 调的是一个 eh_proj(cat(...))，不是两个投影加和。
