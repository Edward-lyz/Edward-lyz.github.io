总体架构

pi-dynamic-workflows 由 5 层组成，每层职责单一。理解每层干了什么，整个 workflow 执行流程就清楚了。

用户问 Pi 一个需要多步的问题 ↓ Pi 模型写一段 JS workflow script，调用 workflow tool ↓ workflow-tool.ts ── parseWorkflowScript() ── acorn AST 解析 + meta 提取 ↓ runWorkflow() ── vm.createContext() 注入 globals ↓ vm.Script.runInContext() ── 在沙箱里执行 script ↓ script 调用 agent(prompt) ── WorkflowAgent.run() ↓ createAgentSession() ── in-memory Pi session（fresh context） ↓ subagent 执行完毕，结果返回给父 workflow ↓ workflow 汇总所有结果，返回给 Pi 主模型

Layer 1：Extension 注册

Pi extension 是一个默认导出函数，接收 ExtensionAPI 对象（简称 pi）。插件在这里注册 tool，并监听 session_start 事件确保 tool 被激活。

// extensions/workflow.ts export default function extension(pi: ExtensionAPI) { const workflowTool = createWorkflowTool(); pi.registerTool(workflowTool); // 把 tool 注册进 Pi 的 tool 注册表 pi.on("session_start", () => { const active = pi.getActiveTools(); if (!active.includes(workflowTool.name)) { pi.setActiveTools([...active, workflowTool.name]); // 确保每次新会话都激活 } }); }
为什么需要 session_start 里再激活一次？ registerTool 只是把 tool 加入候选池，Pi 可能不会自动把它放进当前会话的 active tool 列表。session_start 钩子确保每次新对话开始时 workflow tool 一定对 LLM 可见。

Layer 2：Script 解析与验证

Pi 模型返回一段 JS workflow script 字符串。在执行前，parseWorkflowScript() 用 acorn（标准 JS parser）解析 AST，做两件事：

  1. 提取 meta：第一条语句必须是 export const meta = { name, description }，通过 AST 静态求值，不 eval。
  2. 验证确定性：遍历整个 AST，如果发现 Date.now()、new Date() 或 Math.random() 就抛错。
// workflow.ts — parseWorkflowScript() const ast = parse(script, { ecmaVersion: "latest", sourceType: "module", ... }); assertDeterministicAst(ast); // 遍历 AST 检查非确定性调用 const first = ast.body[0]; // 第一条语句必须是 export const meta const meta = evaluateLiteral(declarator.init); // 静态求值，不 eval，只允许字面量 return { meta, body: script.slice(first.end) }; // body 是去掉 meta 声明后的剩余部分

evaluateLiteral() 是一个递归的白名单求值器，只处理 Literal、ObjectExpression、ArrayExpression，拒绝函数调用、spread、计算属性等。这保证了 meta 的值永远是可信静态数据。

Layer 3：vm 沙箱执行

解析完成后，runWorkflow() 用 Node.js 原生 vm 模块创建一个隔离上下文，把 globals 注入进去，再在这个上下文里运行 script。

// workflow.ts — runWorkflow() const context = vm.createContext({ agent, parallel, pipeline, log, phase, // 编排原语 args, cwd, process, // 只读环境信息 budget, // token 预算追踪 JSON, Math, Array, Object, ... // 白名单的标准库 // 注意：没有 require、import、fs、fetch、Date }); const wrapped = `(async () => {\n${body}\n})()`; const result = await new vm.Script(wrapped).runInContext(context);
沙箱的边界：vm 隔离的是全局变量访问，不是内存。script 无法 require() 或 import 任何模块，也没有 fs、网络 API 或 Date。script 能做的事完全由注入的 globals 决定——这就是为什么 agent() 是唯一的"出口"。

整个 script 被包裹在 async () => {} 里，所以 script 里可以直接 await，runInContext 返回一个 Promise，等待 script 执行完毕。

Layer 4：Subagent Spawn

script 调用 agent(prompt) 时，真正的执行发生在 WorkflowAgent.run()（src/agent.ts）：

// agent.ts — WorkflowAgent.run() const { session } = await createAgentSession({ cwd: this.cwd, agentDir, sessionManager: SessionManager.inMemory(this.cwd), // ← 关键：in-memory，fresh context settingsManager: SettingsManager.create(this.cwd, agentDir), customTools, // coding tools + 可选 structured_output ...this.sessionOptions, }); await session.prompt(this.buildPrompt(prompt, options)); // 发一条消息给 subagent // 等待 subagent 完成，返回最后一条 assistant 文本（或 structured output）

每个 agent() 调用都 createAgentSession 一次，产生一个完全独立的 Pi session：

  • SessionManager.inMemory()：session 不落盘，会话历史隔离，不继承父 session 的上下文。
  • Subagent 拥有完整的 coding tools（读文件、运行 shell 等），可以独立工作。
  • 如果传了 opts.schema，还会注入一个 structured_output tool，subagent 的最后动作必须调用它，确保输出符合 JSON Schema。
这和 Subagent 设计哲学课里讲的 fresh context 原则完全一致：每个 subagent 从空白状态出发，不受父 session 的 context pollution 影响，判断更准确。

Layer 5：编排原语

vm 沙箱里注入了三个编排原语。理解它们的实现，就能预测它们的行为。

agent(prompt, opts)

const agent = async (prompt, agentOptions = {}) => { const run = limiter(async () => { // 并发限制器：默认 max(1, CPU-2) 个，最多 16 state.agentCount++; const result = await agentRunner.run(prompt, { ... }); state.spent += estimateTokens(result); return result; }); pendingAgentRuns.add(run); // 追踪所有未完成的 agent，用于 abort return run; // 返回 Promise，script 用 await 等待 };

并发控制：createLimiter(n) 实现了一个简单的信号量队列，同时最多 n 个 subagent 在运行。超出的调用进队列等待。

parallel(thunks)

const parallel = async (thunks) => { // thunks 是函数数组，不是 Promise 数组 return Promise.all(thunks.map(async (thunk, index) => { try { return await thunk(); } catch { log(`parallel[${index}] failed`); return null; } })); };

参数必须是 函数（() => agent(...)），不是 Promise。这是因为如果直接传 Promise，agent 在传入前就已经开始执行，无法受 limiter 控制。包成函数是延迟求值的标准做法。

pipeline(items, ...stages)

const pipeline = async (items, ...stages) => { return Promise.all(items.map(async (item, index) => { let value = item; for (const stage of stages) { // 每个 item 串行过所有 stage value = await stage(value, item, index); } return value; })); // 不同 item 之间并发 };

同一个 item 在各 stage 之间是串行的（stage 2 必须等 stage 1 的结果），但不同 item 之间是并发的（item 1 和 item 2 可以同时在不同 stage 执行）。这是 fan-out/fan-in 的变体，适合"对每个文件做多步分析"这类任务。

为什么禁止 Date.now() / Math.random()

workflow script 是由 LLM 生成的，并且可能被存储、重放或审计。如果 script 依赖随机数或当前时间，每次执行结果不同，无法重现，也无法对比。

更深层的原因：acorn 在解析时通过 AST 检查这些调用，而不是在运行时 patch。这意味着即使 script 里的 Date.now() 在条件分支里从未被执行到，也会在解析阶段就被拒绝。宁可误杀，不可放过。
合法替代：如果需要"时间"或"唯一标识"，把它放在 args 参数里由调用方传入，或者用 agent prompt 里的 cwd 拼出唯一路径。

检查理解

问题 1

workflow script 里写 await parallel([agent("a"), agent("b")]) 会发生什么？

  • agent("a") 和 agent("b") 同时并发执行，返回结果数组
  • parallel() 收到的是两个已启动的 Promise，两个 agent 已经绕过 limiter 开始运行，且 parallel() 会抛 TypeError
  • 只有 agent("a") 执行，agent("b") 被忽略
  • workflow 被 vm 沙箱拦截，不执行任何 agent
parallel() 期望接收函数（() => agent(...)），传入 Promise 会先启动 agent（绕过 limiter），然后 parallel() 内部检测到不是函数会抛 TypeError："parallel() expects an array of functions, not promises."

问题 2

subagent 里有 createAgentSession 和 SessionManager.inMemory()，这意味着什么？

  • subagent 的对话历史会保存到磁盘，可以跨会话复用
  • subagent 从空白上下文启动，没有父 session 的历史，任务结束后内存被释放
  • subagent 继承父 session 的全部工具和上下文，只是独立运行
  • subagent 只能读文件，不能执行 shell 命令
inMemory() 创建的 SessionManager 把会话历史存在内存里（不落盘），session.dispose() 调用后释放。每个 agent() 调用都是 fresh context，与 subagent-design-philosophy 里讲的 fresh vs fork 原则一致。

问题 3

pipeline(items, stage1, stage2) 里，item1 的 stage1 和 item2 的 stage1 之间的关系是？

  • item1 的 stage1 必须先完成，item2 的 stage1 才能开始（串行）
  • item1 的 stage1 和 item2 的 stage1 并发执行（受 limiter 控制）
  • 两个 stage1 顺序不确定，取决于 agent 响应速度
  • pipeline 不支持多个 item 并发，本质是串行
pipeline 用 Promise.all(items.map(...)) 让不同 item 并发执行。每个 item 内部串行（stage1 → stage2），但 item1 和 item2 可以同时各自在 stage1 运行。并发度受全局 limiter 约束。
