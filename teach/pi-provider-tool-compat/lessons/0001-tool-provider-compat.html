问题：N 个模型 × M 个工具

pi 支持 OpenAI、Anthropic、Google、Mistral、Bedrock 等十几家 provider。它们的 tool calling 线格式（wire format）互不相同：OpenAI 把参数包在 function.parameters 里，Anthropic 叫 input_schema，Google 叫 parametersJsonSchema。

如果让每个工具去适配每个模型，就是 N × M 份适配代码。加一个 provider 要改所有工具，加一个工具要懂所有 provider。这是组合爆炸。

pi 的答案是经典的 hub-and-spoke（中心辐射）：在所有 provider 中间放一套与 provider 无关的 canonical IR（规范中间表示）。工具只面向 IR 写一次，每个 provider 只写一个 IR ↔ 自己格式的 adapter。于是 N × M 塌缩成 N + M。

解法：中间放一套 canonical IR

这套 IR 定义在 @earendil-works/pi-ai/dist/types.d.ts，是整个兼容层的"普通话"。几个核心类型：

类型含义
Tool{ name, description, parameters }——parameters 是 TypeBox schema
Context{ systemPrompt?, messages, tools? }——一次请求的全部输入
ToolCall{ type:"toolCall", id, name, arguments }——模型要调用的工具
ToolResultMessage{ role:"toolResult", toolCallId, content, isError }——工具执行结果
Model<TApi>带 api、provider、baseUrl、compat 等字段的模型描述

所有 pi 内部代码（agent loop、你写的工具、subagent）都只跟这套 IR 打交道。模型差异被关在 provider adapter 里。

你的工具 / agent loop │ 只认 canonical IR（Tool / Context / ToolCall） ▼ ┌─────────────────────────────┐ │ pi-ai：stream(model, ctx) │ ← 唯一入口 └─────────────────────────────┘ │ 按 model.api 分发 ├──────────┬──────────┬──────────┬─────────┐ ▼ ▼ ▼ ▼ ▼ anthropic openai- openai- google- bedrock- -messages completions responses generative converse │ │ │ │ │ 各自 convertTools / convertMessages，翻译成自己的 wire format ▼ ▼ ▼ ▼ ▼ Claude GPT/ GPT/ Gemini Bedrock (incl. 兼容厂商 Codex Claude Code)

工具只定义一次（TypeBox = JSON Schema）

关键设计：工具的参数用 TypeBox 描述，而 TypeBox 直接就是 JSON Schema（运行时是普通 JSON 对象，带一点 Symbol 元数据）。这一点是整个兼容性的地基——因为所有主流 LLM API 的 tool 参数都接受 JSON Schema。

// pi docs · extensions.md — 注册一个工具 pi.registerTool({ name: "greet", label: "Greet", description: "Greet someone by name", parameters: Type.Object({ // ← TypeBox，本质是 JSON Schema name: Type.String({ description: "Name to greet" }), }), async execute(toolCallId, params, signal, onUpdate, ctx) { return { content: [{ type: "text", text: `Hello, ${params.name}!` }], details: {} }; }, });

你在上一课（workflow 实现原理）见过 subagent 拿到的 customTools，它们就是这种 AgentTool。同一个定义，下面会被翻译给任意模型。

源码里 convertTools 注释反复写着一句话：// TypeBox already generates JSON Schema。也就是 tool.parameters 这块 schema body 几乎是原样透传的，provider adapter 只负责换外层信封。

分发点：API registry 与 model.api

多态发生在一个很小的地方。pi-ai 维护一个 Map<api, {stream, streamSimple}> 注册表，启动时把 9 个内置 API 注册进去：

// register-builtins.js registerApiProvider({ api: "anthropic-messages", stream: streamAnthropic, ... }); registerApiProvider({ api: "openai-completions", stream: streamOpenAICompletions, ... }); registerApiProvider({ api: "openai-responses", stream: streamOpenAIResponses, ... }); registerApiProvider({ api: "google-generative-ai",stream: streamGoogle, ... }); registerApiProvider({ api: "bedrock-converse-stream", ... }); // 等等，共 9 个

真正的请求入口 stream() 只做一件事：拿 model.api 当 key 查表，调对应的实现。

// stream.js — 整个分发逻辑就这么点 export function stream(model, context, options) { const provider = getApiProvider(model.api); // ← 按 api 查注册表 if (!provider) throw new Error(`No API provider for: ${model.api}`); return provider.stream(model, context, withEnvApiKey(model, options)); }
这就是兼容多模型的 seam（接缝）。model.api 是一个开放字符串类型（KnownApi | (string & {})），所以 pi.registerProvider() 注册的自定义 provider 可以挂上自己的 streamSimple，无需改动任何上层代码。加模型 = 往 Map 里加一项。

convertTools：同一份 schema，四种信封

这是本课最该记住的一张表。每个 provider 的 convertTools 都接收同一个 Tool[]，输出不同 wire format，但 schema body（tool.parameters）是共享的：

API输出形状（信封）schema 放哪
openai-completions{ type:"function", function:{ name, description, parameters }}function.parameters 原样透传
openai-responses{ type:"function", name, description, parameters, strict }顶层 parameters（不嵌套）
anthropic-messages{ name, description, input_schema:{ type:"object", properties, required }}拆出 properties/required 塞进 input_schema
google-generative-ai{ functionDeclarations:[{ name, description, parametersJsonSchema }]}parametersJsonSchema 原样透传

对比 OpenAI 和 Anthropic 两段真实源码，差异一目了然：

// openai-completions.js — convertTools return tools.map((tool) => ({ type: "function", function: { name: tool.name, description: tool.description, parameters: tool.parameters, // TypeBox already generates JSON Schema }, })); // anthropic.js — convertTools return tools.map((tool) => ({ name: tool.name, description: tool.description, input_schema: { // ← Anthropic 管它叫 input_schema type: "object", properties: tool.parameters.properties ?? {}, required: tool.parameters.required ?? [], }, }));
第一性原理：之所以能这么省事，是因为 pi 选择把 IR 的工具参数直接做成 JSON Schema。各家 API 在 tool 参数上本来就向 JSON Schema 收敛，所以"翻译"退化成"换个字段名 / 套个外壳"。选对 IR，适配器就薄。

回程：把 tool call 解析回 canonical ToolCall

出站（pi → 模型）是 convertTools。入站（模型 → pi）是反向：每个 provider 的流解析器把自己格式的 tool call 事件，统一成 canonical ToolCall { id, name, arguments }。上层 agent loop 永远只看到这一种形状。

这里有个跨 provider 的脏活：tool call ID 归一。OpenAI Responses API 生成的 ID 可能 450+ 字符、含 | 等特殊符号；而 Anthropic 要求 ID 匹配 ^[a-zA-Z0-9_-]+$ 且 ≤64 字符。当你把一段对话历史从一个模型接力给另一个模型（cross-provider handoff），transformMessages() 会重写这些 ID，保证下游 API 不报错。

// transform-messages.js // Normalize tool call ID for cross-provider compatibility. // OpenAI Responses API generates IDs that are 450+ chars with special chars like `|`. // Anthropic APIs require IDs matching ^[a-zA-Z0-9_-]+$ (max 64 chars).

同一个文件还顺手做了另一件兼容活：如果目标模型不支持图像（model.input 不含 "image"），就把消息里的图片替换成 (image omitted: ...) 占位文本，而不是直接报错。

compat flags：吸收 provider 怪癖

光有 convertTools 还不够，因为同样号称"OpenAI 兼容"的厂商各有怪癖。pi 用一组 compat 布尔开关来吸收这些差异。detectCompat() 先按 provider / baseUrl 自动探测，getCompat() 再让显式配置覆盖探测值：

compat flag解决的怪癖
supportsDeveloperRolereasoning 模型用 developer 角色还是退回 system
maxTokensField用 max_completion_tokens 还是老的 max_tokens
requiresToolResultNametool result 消息是否必须带 name 字段
thinkingFormatthinking 参数格式：openai / deepseek / qwen / zai / together ...
supportsStrictModetool 定义里能否带 strict 字段（有些厂商会拒绝未知字段）

例如 Moonshot、Together、Cloudflare AI Gateway 等被探测为"非标准"，pi 自动给它们用 max_tokens 并去掉 strict。这意味着接一个新的 OpenAI 兼容端点，通常不写代码，只在 models.json 里设几个 compat flag 就行（见 models.md）。

Claude Code 的特殊处理

你的问题特意点了 Claude Code，它确实是个有意思的特例。当 API key 是 Anthropic 的 OAuth token（以 sk-ant-oat 开头，来自 Claude Pro/Max 订阅登录），pi 必须把自己伪装成 Claude Code CLI 才能用这条订阅通道。anthropic.js 里做了三件事：

  1. 身份 headers：加上 user-agent: claude-cli/<version>、x-app: cli、anthropic-beta: claude-code-20250219,oauth-2025-04-20。
  2. 强制 system prompt：第一条 system 文本必须是 "You are Claude Code, Anthropic's official CLI for Claude."，你真正的 system prompt 拼在后面。
  3. 工具名归一：toClaudeCodeName() 把工具名按大小写映射回 Claude Code 的官方写法——read → Read、bash → Bash、edit → Edit 等（共 18 个 CC 内置工具名）。
// anthropic.js function isOAuthToken(apiKey) { return apiKey.includes("sk-ant-oat"); } const claudeCodeTools = ["Read","Write","Edit","Bash","Grep","Glob", "AskUserQuestion","EnterPlanMode","ExitPlanMode","KillShell", "NotebookEdit","Skill","Task","TaskOutput","TodoWrite","WebFetch","WebSearch"]; const toClaudeCodeName = (name) => ccToolLookup.get(name.toLowerCase()) ?? name; // convertTools 里： name: isOAuthToken ? toClaudeCodeName(tool.name) : tool.name,
注意这个映射是双向的：出站把 read 改成 Read 发给 Claude；入站 fromClaudeCodeName() 再把模型返回的 Read 映射回你工具的真实名字 read，这样上层 agent loop 完全无感。兼容的代价被精确地隔离在 anthropic adapter 内部——这正是 hub-and-spoke 的价值：脏活只发生在辐条末端，中心保持干净。

所以"兼容 Claude Code"不是一个独立机制，而是同一套 adapter 模式的一个分支：检测到 OAuth → 走 CC 身份 + 工具名归一，其余照旧。

检查理解

问题 1

pi 用同一份 tool.parameters 喂给 OpenAI 和 Anthropic，靠的是什么前提？

  • pi 在运行时为每个模型重新生成一份专用 schema 对象
  • TypeBox 定义本身就是 JSON Schema，各家 API 的 tool 参数都收敛到 JSON Schema，翻译只需换信封
  • pi 把所有工具参数都序列化成字符串，模型自己解析
  • OpenAI 和 Anthropic 的 tool 格式其实完全一样，无需翻译
TypeBox schema 运行时就是带元数据的 JSON 对象。convertTools 注释明说 "TypeBox already generates JSON Schema"，schema body 原样透传，OpenAI 套 function.parameters、Anthropic 拆进 input_schema，只是外层信封不同。

问题 2

要给 pi 接一个全新的、API 格式非标准的模型 provider，最小改动发生在哪里？

  • 修改 agent loop 和每一个已注册的工具，让它们认识新格式
  • 改写 canonical IR 的类型定义，增加新字段
  • 用 registerProvider 注册一个新 api 名 + 自己的 streamSimple，registry 按 model.api 分发，上层无感
  • 在 stream() 里加一个 if-else 分支判断新 provider
分发是 getApiProvider(model.api) 查表，api 是开放字符串类型。注册新 provider 等于往 Map 加一项，stream() / agent loop / 工具一行都不用动。这就是 seam 的意义。

问题 3

用 Claude Pro 订阅（OAuth token）跑 pi 时，工具名 read 会怎样？

  • 原样 read 发给 Claude，返回也是 read，无特殊处理
  • 出站归一成 Read（CC 官方写法），入站再映射回 read，上层无感
  • 被拒绝，OAuth 通道不允许自定义工具
  • pi 自动改用 OpenAI 通道绕开 Claude Code 限制
检测到 sk-ant-oat token 时，pi 伪装成 Claude Code CLI：toClaudeCodeName 出站把 read→Read，fromClaudeCodeName 入站把 Read→read。脏活全锁在 anthropic adapter 内，hub-and-spoke 的辐条末端。
