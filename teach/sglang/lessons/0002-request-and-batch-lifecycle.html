Req 与 ScheduleBatch 的双重生命周期

学完本课，你能拿任意 request id，判断它当前属于 waiting、extend、running decode、finished 还是 retracted，并指出状态保存在哪个对象中。

先把两种生命周期分开

Req 是跨 forward 存活的请求状态，持有输入、输出、采样参数、prefix match、request row、KV 长度与完成原因；ScheduleBatch 是一次 forward 的执行快照，持有本轮 requests、forward mode、flatten 后的 input、sequence lengths、KV 输出位置和采样 metadata。把二者混成一个概念，就会误以为 prefill batch 执行后已经消失的 request 也消失了。

正常 request 的主状态线

IPC request
  → handle_generate_request
  → _add_request_to_queue
  → waiting_queue
  → get_new_batch_prefill → ScheduleBatch(EXTEND)
  → process_batch_result
  → 下一轮把 last_batch 合入 running_batch
  → update_running_batch → ScheduleBatch(DECODE)
  → ...多轮 decode...
  → finish → cache_finished_req / release request row

handle_generate_request 负责把外部请求变成内部 Req，完成长度、session、LoRA、cache key 等初始化；_add_request_to_queue 决定进入普通 waiting queue、grammar queue 或 feature-specific queue。本课程只追普通生成路径。依据：scheduler.py:2034-2318。

最反直觉的边界在两轮之间

当前循环执行完 EXTEND 后，batch 被保存为 last_batch。下一次 get_next_batch_to_run 才过滤已经结束或仍需 chunk 的 requests，并把其余 requests 合入 running_batch。随后 Scheduler 仍先尝试构造新的 prefill；只有没有可运行的新 prefill 时，才对 running_batch 调用 update_running_batch 并执行 decode。

loop N:   EXTEND(A, B) ──result──→ last_batch
loop N+1: filter(last_batch)
          merge A, B into running_batch
          try new EXTEND(C)
          if none: DECODE(A, B)
调度优先级不等于 request 优先级默认主干是本轮有可运行 prefill 就先执行 prefill，否则才执行 running decode。waiting queue 内部怎样排序，是另一个 policy 层问题。

依据：scheduler.py:2598-2729。

实际走读时，为每个 rid 同时记录 queue/container、forward_mode、req_pool_idx、kv_committed_len 和 last_node。只记录 queue 会看不到 physical ownership，只记录 batch 又会看不到跨轮 request 语义。Result processing 正是在这两本账之间完成提交。依据：scheduler.py:3449-3568。

Retracted 不是新 request

decode 内存不足时，部分 Req 会释放当前 request row 和 KV，设置 retraction 相关状态，再由 Scheduler 以 is_retracted=True 放回 queue。它保留生成历史与用户语义，但后续必须重新建立 prefix/KV ownership。因而排障时要同时问两件事：request 的逻辑输出是否保留，以及 physical KV 是否仍存在。
