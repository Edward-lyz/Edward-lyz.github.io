Prefill admission 与 token budget

学完本课，你能区分 waiting queue 排序与 admission，并用 PrefillAdder 的四类约束手算一个 request 能否进入本轮 prefill。

Admission 控制的是未来峰值

一个新 request 不只消耗当前要 prefill 的 token。Scheduler 还要考虑已经运行 requests 的未来 decode、该 request 的 max_new_tokens、页对齐开销，以及可从未锁定 Radix Cache 回收的空间。标准 MHA 路径可压缩成：

available_and_evictable
  = allocator.available_size() + tree_cache.evictable_size()

rem_total_tokens
  = available_and_evictable - running_future_reservation

new_request_total_reservation
  = ceil_page(extend_tokens) + max_new_tokens + page_size

new_request_current_reservation
  = ceil_page(extend_tokens) + page_size

rem_total_tokens 防止当前 prefill 能跑、后续 decode 却立即爆仓；cur_rem_tokens 防止本轮 allocation 本身超配。Hybrid SWA、Mamba 与 DLLM 有额外预算，本课先固定标准 MHA。依据：schedule_policy.py:433-690。

四道门必须同时通过

约束它保护什么典型字段
KV 总预算running 与新请求的未来 lifetimerem_total_tokens
本轮输入预算单次 forward 的 prefill 工作量rem_input_tokens
Chunk 预算长 prompt 对 decode latency 的干扰rem_chunk_tokens
Request slotReqToTokenPool row 与 batch 上限max_running_requests

get_new_batch_prefill 先按 schedule policy 排 waiting queue，再让 PrefillAdder 逐个尝试。遇到 NO_TOKEN 通常停止继续添加；遇到 request count、LoRA 或其他边界，也可能返回 OTHER。所以 waiting queue 非空不意味着本轮一定有 prefill。依据：scheduler.py:2733-2955。

Policy 排顺序，PrefillAdder 决定能否运行

Policy排序信号主要收益主要风险
fcfs到达顺序简单、公平忽略 cache locality
lpm最长 cached prefix减少 extend compute匹配与排序有 CPU 成本
dfs-weightRadix subtree weight批内共享与 locality行为依赖 tree shape
lof/random/routing-key输出长度、随机或 routing frequency面向特定 workload不能自动保证 KV 可容纳

SchedulePolicy.calc_priority 只改变 waiting queue 的候选顺序；每个候选仍要经过 PrefillAdder。v0.5.15 还有一个容易漏读的边界：配置 lpm 但 waiting queue 超过 128 时，active policy 临时退回 FCFS，避免大队列上的 prefix matching 与排序成本。看到 LPM ordering 消失或 cache locality 改变时，应先检查 active policy，而不是断言 Radix Cache 失效。依据：schedule_policy.py:138-250。

Locality 不能绕过 capacityLPM 排在第一的 request 若无法通过 lifetime、current、chunk 或 row budget，仍然不能进入本轮 batch。

手算一个标准路径

设 page_size=16，allocator 有 2,000 token slots，Radix Cache 有 400 个未锁定可驱逐 slots，running requests 的未来 reservation 为 1,500。候选 request cache hit 后还需 extend 320 tokens，max_new_tokens=128。

rem_total = 2000 + 400 - 1500 = 900
reserve   = ceil_page(320) + 128 + 16
          = 320 + 128 + 16 = 464
remaining = 900 - 464 = 436

它通过总预算，但还要检查本轮的 max_prefill_tokens、chunk budget 和 request row。如果 extend 为 321，页对齐会把它变成 336，这种看似小的差异在大 batch 下会累计。

不要把 evictable 当成 freeevictable_size 只是 Scheduler 可以按需回收的承诺。真正分配前，allocator 路径仍会调用 tree eviction；锁定节点不在这笔预算中。

Pool capacity 与动态 reservation 是两层控制

mem_fraction_static 参与启动期的 GPU memory 划分，决定 model weights 与 KV pool 可占的静态比例；new_token_ratio 不扩缩这个 pool，而是在 admission 时估计 running requests 未来还会生成多少 tokens。成功 decode 会逐步衰减 ratio，提高利用率；发生 retraction 后，tracker 根据当前 requests 的 decoded/max-new 状态重新估计，使后续 admission 更保守或更符合当前 workload。

startup capacity:
GPU memory → weights + KV pool + activations + graph buffers

runtime promise:
KV pool slots → free + evictable - estimated future tokens

所以调大 mem_fraction_static 与调低调度保守度不是同一操作：前者改变池的物理上限并挤压 activation/graph headroom，后者改变池内 overcommit 风险。依据：server_args.py:3470-3495 与 new_token_ratio_tracker.py:12-50。

读日志时的因果顺序

  1. 先看 waiting queue 是否有可运行 request。
  2. 再看 request row 与 batch count。
  3. 再看 rem_input_tokens 和 chunk budget。
  4. 最后区分 free、evictable、protected 与 running reservation。

只看 nvidia-smi 无法回答 admission 问题，因为 KV pool 在启动时已预分配，调度关心的是池内 slot ownership。

最小自检

page_size=16，extend 为 321，max_new_tokens=128。标准路径的 lifetime reservation 是多少？

正确。ceil_page(321)=336，所以 336 + 128 + 16 = 480。
不对。先按 16 对齐到 336，再加 128 个未来输出 slots 和一个 16-token page overhead。

配置 lpm，但 waiting queue 超过 128。v0.5.15 当前 pass 使用什么 active policy？

正确。大于 128 时临时使用 FCFS，避免大队列 prefix matching 与 sorting 开销。
不对。配置仍是 LPM，但这个 pass 的 active policy 临时回退为 FCFS。
