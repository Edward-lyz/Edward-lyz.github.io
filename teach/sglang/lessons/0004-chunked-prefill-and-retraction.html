Chunked prefill 与 retraction

学完本课，你能区分 chunked prefill 的主动切片与 decode retraction 的内存恢复，并追踪二者如何回到 waiting side。

两种机制解决两个不同问题

机制触发时机目的KV 后果
Chunked prefilladmission 时 prompt 超过 chunk budget限制单轮 prefill，避免长 prompt 长时间阻塞已算 chunk 被 cache，request row 可复用
Decode retraction下一轮 decode KV 不足立刻回收正在运行 request 的空间释放 KV，不把临时状态插入 Radix Tree

前者是计划内的工作分片，后者是压力下的 preemption。把 retraction 叫作 chunking 会掩盖一次昂贵的重算。

Chunked request 跨轮怎样存活

waiting request: fill_len = 10,000
chunk budget: 2,048

round 1: extend [0, 2048)   → stash/cache this chunk
round 2: extend [2048,4096) → stash/cache this chunk
...
last round: complete extend  → merge into running decode

PrefillAdder.add_chunked_req 设置本轮 extend_range；若 truncated，就把同一个 Req 保存在 chunked_req。下一轮选批开头，它从上一批的 merge 集合中被排除，刚产生的 KV 通过 stash_chunked_request 缓存，再初始化下一段。这样未完成 prompt 不会被误当成可 decode request。依据：schedule_policy.py:730-790 与 scheduler.py:2610-2675。

Decode 先驱逐 cache，再 retract requests

update_running_batch 先过滤 finished requests，然后调用 check_decode_mem。后者先尝试从 Radix Cache 驱逐未锁定节点；若 physical slots 仍不足，才进入 retract_decode。

filter finished
→ estimate next-decode allocation
→ evict unlocked radix leaves
→ enough? decode
→ not enough? retract selected requests
→ release their request row + KV immediately
→ requeue as retracted
→ recompute future-token ratio

选择策略在非 speculative path 中会参考已生成长度和 prompt 长度。循环至少保留一个 request；但若最后一个 request 仍不能 forward，v0.5.15 会明确 abort 它并返回错误，而不是静默换成另一种执行语义。依据：scheduler.py:3041-3124 与 schedule_batch.py:2470-2550。

Retract 的代价不是一次 queue move逻辑输出历史仍在，但其 physical KV 被释放。再次 admission 时要重新 match cache，并可能重算未进入共享树的部分。指标应同时看 retraction 次数、重算 token 与 tail latency。

Retract 会把 physical frontier 归零

reset_for_retract 保留 rid、输入、已生成输出和 sampling 语义，但把 prefix_indices、last_node、request row 关联以及 committed/allocated KV frontiers 清零，并永久标记 retracted_stain。再次进入 admission 时，它必须重新 match 当前 tree；能复用多少取决于那一刻仍在 tree 中的 canonical prefix，不等于 retract 前曾经计算过多少。

logical state kept:   input ids + output ids + finish policy + rid
physical state reset: req row + private KV + prefix lock + KV frontiers
next cost:            fill length - newly matched canonical prefix

这解释了 retraction amplification：一次撤回不仅让当前 decode 少一个 request，还可能把大量 private decode history 变成后续 extend 重算。优化目标应是减少 reprocessed tokens，而不只是减少日志中的 retract request count。依据：schedule_batch.py:1438-1471 与 schedule_batch.py:1590-1620。

故障定位模板

  1. 若 TTFT 出现周期性尖峰，先检查 chunk size 与 prefill/decode 交错。
  2. 若 ITL 与吞吐同时抖动，检查 KV cache pool is full. Retract requests 日志。
  3. 若 available 很低但 retraction 不发生，检查可驱逐 cache 是否先释放了足够空间。
  4. 若同一 request 多次 retracted，检查 max_running_requests、max_new_tokens 分布与 admission reserve，而不是只增大 chunk。

最小自检

Decode 的下一步 KV allocation 不足时，标准恢复顺序是什么？

正确。先驱逐未锁定 Radix leaves；仍不足才 retract requests；被撤回的 request 释放 KV 后重新排队。
不对。标准路径先回收 evictable prefix cache，再撤回 running requests，最后把撤回请求重新放回 queue。
