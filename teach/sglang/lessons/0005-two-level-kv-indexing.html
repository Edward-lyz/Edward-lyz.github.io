两级 KV 索引

学完本课，你能估算 per-rank KV tensor 量级，从 request 的逻辑 position 查到 physical slot，并解释为什么 request row 与 KV slot 必须分别分配。

先确定课程讨论的是哪一层优化

层次典型手段是否改变模型/KV语义
Token level选择、稀疏、量化、低秩、merge常需 accuracy 证明
Model levelMQA/GQA/MLA、跨层共享、线性注意力由架构或训练决定
System levelpaging、prefix reuse、tiering、调度、PD核心路径可做无损管理

本课程主线是 system-level ownership：不删除 token，也不改变 attention 数学结果，而是决定 KV 存在哪里、由谁引用、何时迁移或回收。Sparse attention 与 KV compression 可以叠加，但必须另做等价性或 accuracy 验证，不能和 allocator 优化混为一谈。分类背景：A Survey on Efficient Inference for Large Language Models；具体 SGLang ownership 仍以固定 tag 源码为准。

先用公式估算物理量级

标准 MHA/GQA 的每-rank KV bytes 可写成：

M_rank = layers × T_local × bytes_per_element
         × (local_k_heads × k_head_dim + local_v_heads × v_head_dim)

T_local 是该 rank 实际拥有的 request tokens 总数；DPA 会改变它，TP/attention TP 会改变 local heads。公式还没包含 padded page、预留 slot、allocator metadata、HiCache host copy 或 speculative tail，所以它是 lower-level tensor 估算，不是 nvidia-smi 的完整预测。

举一个量级校验：64 层、batch 4、sequence 32,768、总 KV dim 1,024、BF16 时，逻辑未分片 KV 为 2 × 64 × 4 × 32768 × 1024 × 2 bytes = 32 GiB。部署时再把总 KV dim 换成本 rank pool 的真实 heads/dims。这个算式能在读 allocator 前先暴露并发与上下文长度的线性压力。

页表与物理内存是两个资源池

ReqToTokenPool.req_to_token[req_pool_idx, logical_position]
                                │
                                └── physical_kv_slot
                                      │
                                      ├── K[layer][slot, local_kv_head, head_dim]
                                      └── V[layer][slot, local_kv_head, v_head_dim]

ReqToTokenPool 是二维映射表，而不是 KV tensor。本行代表一个活跃 request，本列代表 sequence 内的逻辑位置，值才是实际 KV slot。TokenToKVPoolAllocator 管理这些 physical slots；MHATokenToKVPool 保存每层真正的 K/V buffers。

依据：memory_pool.py:242-320、allocator/token.py:28-82 与 memory_pool.py:1291-1535。

逻辑 sequence 连续，不要求 physical slots 连续。前两个 slots 可能来自 Radix prefix，后两个来自本轮 allocator。Attention backend 通过 request row 和 sequence metadata gather 正确位置。

为什么 row 0 与 slot 0 都保留

ReqToTokenPool 实际分配 size + 1 行，free rows 从 1 开始；CUDA Graph padded batch 的 dummy request index 默认写到 row 0。标准 token allocator 同样把 slot 0 保留给 padded token 的 dummy output。Paged allocator 则保留一个 padded page。它们是两个不同层面的哨兵，不应当合并理解。

两个 allocator 的失败含义不同request row 用尽通常意味着并发 request 上限过高；physical KV slot 用尽意味着 token footprint 过高。二者需要不同参数与诊断。

Page size 改变分配粒度，不改变抽象

page_size=1 时 allocator 逐 token slot 分配。page_size>1 时 PagedTokenToKVPoolAllocator 管理 pages，并返回 page 内展开后的 token indices。request row 仍然保存每个逻辑 token 对应的 physical index，因此上层 lookup contract 不变，但 prefix match、eviction 与 reservation 都必须 page aligned。依据：allocator/paged.py:105-250。
