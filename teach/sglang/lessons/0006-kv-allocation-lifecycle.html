KV allocation 生命周期

学完本课，你能逐行解释 extend、decode 与 finish 三条路径怎样创建、提交、复用和释放 request row 与 physical KV slots。

Extend 是批量建表

  1. prepare_for_extend 计算每个 request 的 prefix_lens、extend_lens 与新 seq_lens。
  2. alloc_req_slots 为新 request 分配 row；chunked request 可复用既有 row。
  3. allocator 为全部 extend tokens 分配 physical slots 或 pages。
  4. write_cache_indices 先写 cached prefix indices，再写本轮新 slots。
  5. request 的 kv_committed_len 与 kv_allocated_len 更新到本轮 sequence end。
row r before: [prefix slot 8, prefix slot 9, ...]
new slots:                              [31, 45, 46]
row r after:  [8, 9, 31, 45, 46]
                               └─ out_cache_loc ─┘

依据：mem_cache/common.py:452-529 与 schedule_batch.py:2011-2145。

Decode 是每个活跃 request 追加一个位置

普通非-spec decode 为 batch 中每个 request 分配一个 slot。写入位置是旧的 seq_lens，随后 prepare_for_decode 把 request 的 committed/allocated lengths 与 batch sequence lengths 各加一。

old seq_len = 5
allocate slot 90
req_to_token[row, 5] = 90
kv_committed_len += 1
kv_allocated_len += 1
seq_len += 1

顺序很重要：页表写在旧 length 指向的新 token 位置，然后 length 才表示包含该位置的新长度。Paged path 会根据上一 slot 和 page boundary 决定复用当前 page 还是获取新 page。依据：mem_cache/common.py:581-635 与 schedule_batch.py:2618-2678。

Scheduler 分配位置，Attention backend 完成读写

Scheduler / allocator:
  choose out_cache_loc + write request page table

Attention backend for this layer:
  write new K/V → token_to_kv_pool[out_cache_loc]
  read history → page table / backend metadata → layer K/V buffer
  run attention → output hidden states

out_cache_loc 是 Scheduler 与 kernel/backend 的契约。Scheduler 不计算 K/V，只承诺本轮每个新 token 应写到哪些 physical slots；backend 在每一层先通过 set_kv_buffer 写入，再用本轮 metadata 读取完整可见 history。FlashInfer、Triton、MLA 或 sparse backend 的具体 layout 可以不同，但不能改变 request row 指向正确 physical ownership 这一不变量。依据：base_attn_backend.py:155-239 与 flashinfer_backend.py:1107-1145。

Mapping 正确不代表 buffer 已写入Allocation 只建立 destination；该 layer forward 真正执行 set_kv_buffer 后，slot 才包含可读的 K/V。PD transfer 也遵守同一 destination-before-data 原则。

Committed 与 allocated 为什么分开

普通路径中二者经常相等，但 overlap 与 speculative paths 可能预分配尚未成为正式 sequence 的 slots。kv_committed_len 是已经可被请求语义承认的 KV frontier；kv_allocated_len 是当前实际占有的 physical frontier。释放时必须 trim overallocated tail，否则 allocator 账面会泄漏。

Finish 不是简单 free 全部 slots

finish
→ pop committed KV length
→ insert page-aligned token/KV pairs into Radix Tree
→ free duplicate slots already represented by canonical tree nodes
→ free unaligned tail
→ release prefix lock
→ release request row

若 prefix cache 被禁用或这次明确不插入，则对应 slots 直接释放。开启 Radix Cache 时，仍可复用的 KV ownership 从 request 转交给 tree；request row 则回到 row pool。两个资源的生命周期因此在 finish 处发生分叉。依据：radix_cache.py:437-487 与 mem_cache/common.py:638-693。

Ownership 转移不等于复制finished request 插入 Radix Tree 后，tree 继续引用 canonical physical slots；只释放重复和尾部 slots。用 allocator free count 判断 cache 行为时必须考虑这次转移。

最小自检

普通 decode 前旧 seq_len=5，新分配 slot 90。页表应写到哪一格？

正确。旧长度 5 表示已有 positions 0 到 4，新 token 写在 position 5，然后 sequence length 增至 6。
不对。sequence position 从 0 开始；已有 5 个 token 占 positions 0 到 4，新 slot 写到 position 5。

Scheduler 已分配 out_cache_loc 后，physical slot 何时真正包含本层 K/V？

正确。Allocation 建立 destination，attention layer 的 backend 写入后 slot 才含真实 K/V。
不对。Index allocation 只保留位置；真实 K/V 来自该 layer forward 的 backend write。
