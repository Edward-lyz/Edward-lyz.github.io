Radix eviction 与 Scheduler 耦合

学完本课，你能从 free、evictable、protected 三个数字推导一次 admission 或 decode allocation 会先驱逐哪些节点、何时转为 retraction。

显存账本有三种 ownership

状态含义是否可立即分配
Freeallocator 当前持有的空 slots可以
EvictableRadix Tree 持有且 lock_ref=0先驱逐后可以
Protected活跃 request 的 prefix path 正在引用不可以

Scheduler admission 使用 free + evictable 估计可回收容量；allocator 真正分配时若 free 不足，再调用 tree eviction 把承诺兑现。Protected 不参与这笔预算。依据：schedule_policy.py:550-625 与 mem_cache/common.py:235-285。

Eviction 只能从未锁定叶子开始

1. 收集 evictable leaves
2. 按配置的 eviction strategy 排优先级
3. 弹出一个 lock_ref=0 的 leaf
4. allocator.free(leaf.value)
5. 删除 leaf
6. 父节点若变成未锁定 leaf，再加入候选
7. 达到目标 token 数或无候选时停止

从叶子向上删才能保持共享 prefix 完整。如果一个叶子被锁定，它的所有 ancestors 也因 root-path lock 而受保护；算法不会越过活跃引用删除父 segment。依据：radix_cache.py:563-591。

Finish 与 chunk 让账本重新归一

cache_finished_req 把 committed、page-aligned KV 插入树，释放与已有 canonical prefix 重复的 slots，再释放不对齐 tail 和 prefix lock。cache_unfinished_req 用于 chunked request：插入后重新 match，把 request row 中相关位置改写为 canonical tree indices，避免 request 继续指向已释放的副本。

request-private indices: [301, 302, 303, 304]
tree canonical indices:  [101, 102, 303, 304]
insert + rematch
request row rewritten:   [101, 102, 303, 304]
free duplicates:         [301, 302]

依据：radix_cache.py:437-542。

与 Scheduler 的完整压力路径

prefill admission:
  free + evictable - reservations → admit or stop

extend allocation:
  free insufficient → evict leaves → allocate or fail loudly

decode preparation:
  estimate next slots → evict leaves
  still insufficient → retract running requests
  last request still impossible → explicit abort
Cache hit rate 与可调度容量互相制约锁住更多热门 prefix 可减少 prefill compute，但会降低 evictable headroom。优化不能只追 cache hit；要同时观察 retraction、TTFT、ITL 和有效 token throughput。

最小自检

free 为 80、evictable 为 50、protected 为 500，本次需 120 slots。标准路径先做什么？

正确。可承诺容量为 130，先从 evictable leaves 回收至少 40，使 allocator free 达到 120。
不对。Protected 不能驱逐。因为 free 加 evictable 足够，先从未锁定 leaves 回收缺少的 40 slots。
