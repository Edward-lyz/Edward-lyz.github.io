DP Attention 的 request、KV 与 collective ownership

学完本课，你能追踪一个 DPA request 从 controller 路由、本地 attention/KV，到跨 TP world 的 MLP token gather，并解释空闲 rank 为什么仍要执行 IDLE batch。

Controller 先决定 request ownership

DataParallelController 接收上游请求并按负载策略选择 DP worker。开启 DPA 时，一个 request 只进入一个 attn_dp_rank 的 Scheduler state；该 DP rank 拥有 request row、Radix match 与 KV cache。其他 DP ranks 不保存它的 KV 副本。依据：data_parallel_controller.py:129-235 与 data_parallel_controller.py:456-570。

一个 Transformer layer 内发生 ownership 切换

DP rank local requests
  → local embedding / attention inputs
  → Attention on local request + local KV
  → gather variable token counts across DPA ranks
  → MLP or MoE across original TP world
  → scatter/slice outputs back to each DP rank
  → local sampling / request update

因此 DPA 的收益来自 KV 与 attention workload 的局部化，而不是让整层网络都完全数据并行。Dense MLP 参数仍按 TP shard；MoE 参数可再按 EP shard。每层边界都可能需要重新排列 token buffer。

Scheduler 先同步每个 DP rank 的 token count

各 DP rank 可以独立处于 prefill、decode 或 idle，local token 数不同。DpAttnSchedulerAdapter 把 local forward mode 和 token count 做 all-gather，得到 global_num_tokens，再准备 MLP gather metadata。这个同步发生在真正模型 collective 之前。

rank 2 没有本地 attention，但其他 ranks 有 token 需要通过共享 MLP TP group。若 rank 2 直接跳过本轮，它将不进入 collective，其他 ranks 会挂死。因此 adapter 构造 ForwardMode.IDLE batch，让它以零 local tokens 参与必要的同步。依据：dp_attn.py:47-139 与 dp_attn.py:181-249。

IDLE 是 collective correctness，不是业务工作它不凭空创建 request，也不分配其 KV；它让所有 group members 以一致顺序进入跨-rank MLP path。

TP 8、DPA 8 的完整所有权

  • 进程：8 个 TP Scheduler processes，不是 64 个。
  • Request：controller 选择 1 个 DP rank。
  • KV：该 DP rank 本地 pool 持有。
  • Attention：attn_tp_size=1，本 rank 执行。
  • MLP：8-rank TP world 汇聚 token 并执行参数 shards。
  • 输出：回到 request owner 做采样与状态更新。
