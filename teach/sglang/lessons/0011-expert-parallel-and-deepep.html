Expert Parallel 与 DeepEP

学完本课，你能从 global expert id 推导 weight owner，区分 Dispatcher 与 Runner，并追踪一个 token 经 dispatch、local grouped GEMM 和 combine 返回源 rank。

EP 首先是参数 ownership

对 routed experts，v0.5.15 的核心关系是：

num_local_routed = num_global_routed / moe_ep_size
start = moe_ep_rank × num_local_routed
end   = start + num_local_routed

global expert e belongs to this rank iff start ≤ e < end
local expert id = e - start

例如 256 个 routed experts、ep_size=8，每 rank 拥有 32 个。weight loader 遇到非本 rank expert 会映射为 -1 并跳过；共享 experts 另有映射规则。依据：fused_moe_triton/layer.py:190-225 与 fused_moe_triton/layer.py:690-710。

Token 必须去参数所在 rank

source rank hidden states
  → TopK: token t selects global experts [e7, e91]
  → dispatcher.dispatch
      compute destination layout
      all-to-all token copies to expert owners
  → each rank runs local grouped GEMM
  → dispatcher.combine
      use dispatch handle to send expert outputs back
      apply top-k weights / restore source token order
  → source rank continues the layer

FusedMoE.forward_impl 的稳定骨架是 dispatch → run_moe_core → combine。通信 backend 与 GEMM runner 被分开选择，所以 --moe-a2a-backend 与 --moe-runner-backend 解决不同问题。依据：fused_moe_triton/layer.py:1220-1260。

Dispatcher 与 Runner 是两个独立选择

层CLI负责什么主要瓶颈
TopK routermodel/config选择 global expert ids 与 weightsrouting balance
Dispatcher--moe-a2a-backendtoken dispatch/combine 与 layoutNVLink/RDMA、同步
Runner--moe-runner-backendlocal experts 的 grouped GEMMkernel、quantization、token shape

只替换 DeepEP 会改变通信，不自动改变 local GEMM；只替换 DeepGEMM/Triton runner 也不会消除 all-to-all。Profiler 必须分别记录 dispatch、local compute 与 combine，否则把 end-to-end MoE 时间归咎于一个 backend 没有可证伪性。SGLang 的 FusedMoE.forward_impl 正是用 dispatcher.dispatch → run_moe_core → dispatcher.combine 保持这条边界。依据：Expert Parallelism backend guide 与 fused_moe_triton/layer.py:1220-1260。

DeepEP 的 normal 与 low-latency

模式主要场景Layout 特征
normalprefill / 大 token batch先算 dispatch layout，追求吞吐
low_latencydecode / 小 token batch固定容量 masked layout，兼容 CUDA Graph
auto混合 serving根据 batch 是否包含 extend 动态解析

DeepEPDispatcher._get_impl 读取当前 batch 的 extend 标志：extend 选择 normal，decode 选择 low-latency。其 stage assertions 保证 dispatch 与 combine 顺序配对，dispatch handle 则让 combine 知道结果如何返回源 token。依据：deepep.py:841-970。

DPA 与 EP 是正交 ownership

典型 tp=8, dp=8, ep=8 中，request 与 KV 属于一个 DPA rank，Attention 本地执行；MoE expert weights 分散在 8 个 EP ranks，local attention 输出经 DeepEP 发往选中 expert 的 owner，再 combine 回 request/token 的 source rank。DPA 减少 KV duplication，EP 减少 expert weight duplication，但代价是 MoE all-to-all。

不要从 EP 推导 KV ownershipexpert id 决定 MoE 参数在哪个 rank，request routing 决定 KV 在哪个 DPA rank。这是两套不同映射。

v0.5.15 官方文档说明 DeepEP、Mooncake、NIXL 等多数 A2A backend 要求 ep_size=tp_size；hybrid ep_size<tp_size 通常只能使用非 A2A path。依据：Expert Parallelism guide。
