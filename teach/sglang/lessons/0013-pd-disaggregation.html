Prefill-Decode Disaggregation

学完本课，你能判断 PD 的系统收益是否覆盖 handoff 成本，解释 destination KV 必须先分配的原因，并追踪 PREBUILT 如何进入 decode。

PD 拆开的不是一个 request 的语义

Prefill instance 计算 prompt KV，Decode instance 继续生成；两者拥有独立 Scheduler、request row 与 physical KV pool。request id 与 token history 跨角色保持一致，但 physical slot ids 只在各自进程地址空间内有意义。因此不能把 prefill 的 slot id 直接当成 decode slot id。

PD 不是无条件降低单请求延迟

统一调度PD disaggregation
同一 pool 内完成 prefill 与 decode两个独立 Scheduler/pool 做 handoff
无跨实例 KV transfer增加 bootstrap、metadata 与 KV transfer
Prefill compute 可能阻塞 decode资源专用化，queue 与 interference 可独立控制
容量比例固定在同一实例Prefill/Decode replicas 可按 workload 扩缩

对单个 request，PD path 多了显式 handoff；系统收益来自减少 queueing 与 prefill/decode interference。一个有用的判断式是：

PD worthwhile when:
reduced_queueing + reduced_interference
    > bootstrap + metadata + KV_transfer + staging

这不是源码里的常数公式，而是实验假设。短 prompt、低负载或慢网络下右侧可能占优；长 prompt、高并发和可独立扩容时左侧才可能占优。因此 benchmark 必须报告 transfer bytes/time 与两侧 queue time，不能只比较 model forward。

Decode 先建立目的地址

router sends request metadata to both roles

Decode:
  handshake/bootstrap
  → match optional local decode-side prefix
  → allocate destination request row
  → preallocate destination KV pages
  → send destination page indices + metadata buffer id

Prefill:
  bootstrap sender
  → schedule and compute prompt KV
  → send KV into decode-provided destinations
  → poll transfer completion

Decode:
  poll receiver
  → commit transferred KV to request
  → move request into waiting/prebuilt side
  → ForwardMode.PREBUILT
  → continue normal decode

RDMA/transfer engine 需要目的地址才能发起写入；更重要的是，Decode Scheduler 必须在接收前把这些 pages 计入自己的 memory budget，防止 running decode 同时占用它们。依据：decode.py:275-620 与 prefill.py:104-330。

PREBUILT 表示 KV 已存在，不再重跑 prompt

Transfer 成功后，Decode 侧构造 ScheduleBatch，prepare_for_prebuilt 从已分配 request row 读取 out_cache_loc，填充 sequence metadata，并设置 ForwardMode.PREBUILT。process_prebuilt 接入最后 token、cache 与采样状态。这个 batch 模拟完成后的 prefill transition，但不会重新执行整段 prompt forward。

PREBUILT 是状态衔接，不是 fake KV真实 KV 已由 transfer 写入 Decode pool；PREBUILT 只构造 Scheduler/forward 所需 metadata。

依据：decode_schedule_batch_mixin.py:23-145。

Decode queue 优先恢复 retracted requests

process_decode_queue 先尝试为 retracted requests 恢复预留。如果仍有 retracted requests 无法恢复，它不会继续接纳新的 preallocation；否则才把 preallocated connections 移到 transfer queue，poll completed transfers，并把成功 requests 加到 waiting side。这维持了 memory accounting 与 starvation 边界。依据：decode.py:1973-2005。

异构 TP 与 backend 只改变 transfer contract

Mooncake 与 NIXL 提供不同 transport；prefill/decode TP layout 不一致时可能需要 staging 和 KV head mapping。但不变量不变：Decode 决定 destination ownership，Prefill 只写入已协商目标，成功 commit 后 request 才可进入 PREBUILT/decode。

配置与限制依据：PD disaggregation guide。

最小自检

PD transfer 的正确关键顺序是哪一项？

正确。Decode 先拥有并预留 destination slots，Prefill 才能写入；成功后用 PREBUILT 衔接状态。
不对。Physical slot ids 属于 Decode pool，必须由 Decode 先分配并协商，transfer 成功后才构造 PREBUILT。

哪种 workload 最可能让 PD handoff 成本超过资源专用化收益？

正确。此时可减少的 queue/interference 很小，而 bootstrap 与 KV transfer 仍是固定新增路径。
不对。长 prefill、高干扰和快速 transport 更可能让资源专用化覆盖 handoff 成本。
