先把性能指标写成时间线

request arrival
  ├─ queue + tokenize + prefill ───────────────┤ first token
  │                    TTFT                    │
  └─ first token ─ ITL₁ ─ token₂ ─ ITL₂ ─ ... ─ final token

E2E latency = TTFT + Σ ITL
steady approximation = TTFT + (N_output - 1) × mean_ITL

TTFT 主要暴露 queue、prefix reuse、prefill、HiCache/PD transfer；ITL/TPOT 主要暴露 decode batch、KV bandwidth、DPA/DeepEP collective 与 retraction。Output tok/s 是系统吞吐，不说明单请求 tail。三者必须放在同一 trace 上解释，否则提高 batch size 得到的 throughput 增益可能只是把延迟转嫁给用户。

每组先 warmup，再至少记录相同时间窗的三次独立运行。平均吞吐不能替代 tail latency；cache hit 不能替代有效 compute 节省；GPU utilization 不能解释 queueing。必要指标至少包括 TTFT p50/p99、ITL p50/p99、output tok/s、retracted requests 与 prefix hit tokens。

源码与实验如何闭环

  1. 源码先给出可证伪预测，例如 chunk 变小会增加 prefill rounds，但可能改善 decode interleaving。
  2. 设计唯一变量，确保 admission、模型、到达 trace 不同时变化。
  3. 从 Scheduler 日志或 profiler 识别 batch mode 与 token counts。
  4. 若结果反向，先检查是否触发 retraction、page alignment、DeepEP mode switch 或 rank imbalance。
  5. 只有机制和端到端指标同时支持，才接受结论。
Benchmark 不是配置搜索一次改十个 flags 即使更快，也无法建立因果模型。课程目标是能解释为什么，而不是找到一个偶然最高值。

最小自检

要验证 chunk size 对 ITL 的因果影响，哪种实验最有效？

正确。固定请求 trace、seed、并发和输出分布，只改变 chunk size，才能把 ITL 差异归因到 chunking。
不对。同时改变其他变量无法区分 queueing、memory pressure 与 chunking。应固定 trace，只改变 chunk size。

TTFT 为 100 ms，输出 5 tokens，平均 ITL 为 20 ms。近似 E2E latency 是多少？

正确。首 token 已包含在 TTFT 中，后面有 4 个 token intervals，所以 100 + 4 × 20 = 180 ms。
不对。5 个输出 tokens 之间只有 4 个 ITL；E2E 近似为 TTFT + (N−1)×ITL。
