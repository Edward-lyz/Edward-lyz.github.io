最终 Capstone：从请求到带 benchmark 的 hot-path 修改

完成本课任务后，你能独立产出一份跨 Scheduler、KV Cache、DPA/EP 的调用链分析，并用 correctness tests 与 benchmark 证明一个 hot-path 修改的价值。

场景

固定代码 v0.5.15，8 张 GPU，配置 tp=8, dp=8, ep=8, DPA on, DeepEP auto。请求 A 与 B 共享 3,072-token prefix；A prompt 8,192 tokens，B prompt 4,096 tokens，chunk size 2,048。系统已有 running decode，KV pressure 在 A 的第三个 chunk 后触发一次 retraction。B 的 TopK 选择了远端 experts。

交付一：画出一次请求 trace

不看参考答案，先在纸上或 Markdown 中填写下列六栏，每一栏都写具体函数与 ownership：

  1. 进程：从 DataParallelController 到哪一个 DPA Scheduler rank。
  2. 调度：A/B 的 waiting、chunked EXTEND、last_batch、running DECODE 状态。
  3. KV：request row、3,072 prefix indices、新 physical slots、Radix canonical slots。
  4. 压力：eviction、protected prefix、retraction、requeue 的严格顺序。
  5. 并行：local attention、MLP token gather、TopK、DeepEP dispatch/combine。
  6. 输出：采样结果回到哪个 request owner，finish 后哪些 slots 留在 tree。
展开核对不变量
  • 物理 Scheduler processes 是 8，不是 tp × dp = 64。
  • A/B 各由一个 DPA rank 拥有 request/KV；共享 prefix 只在同一 cache namespace 与 owner 可直接复用。
  • chunked request 在完成前不合入 running decode；每个已完成 chunk 会 stash/cache。
  • decode pressure 先驱逐 unlocked leaves，仍不足才 retract；protected prefix 不可驱逐。
  • Attention 使用本地 request/KV；MoE token 发往 expert owner，combine 回 source token。
  • finish 把 committed、对齐 KV ownership 转给 Radix Tree，释放 duplicate/tail 与 request row。

交付二：做一次故障诊断

假设 benchmark 显示平均 throughput 上升 8%，但 p99 ITL 退化 35%，retraction 从 0 增至每分钟 14 次。你的结论不能是整体更快。先用下列顺序定位：

arrival trace unchanged?
→ prefill/decode batch token counts
→ free / evictable / protected
→ PrefillAdder future reservation
→ page alignment overhead
→ retracted request and recomputed tokens
→ DPA token imbalance / IDLE frequency
→ DeepEP normal vs low-latency resolution

必须给出一个可证伪预测，例如降低 admitted running requests 后 retraction 应下降，若 ITL 不恢复则主要原因不是 KV pressure。

交付三：hot-path 修改

从两条路径选一条，先 profile 再改；如果 profiler 不支持瓶颈假设，应停止修改而不是制造优化。

候选Correctness 基线Benchmark 基线
PrefillAdder.add_one_req 或 budget calculationtest/registered/unit/managers/test_prefill_adder.py固定 waiting/running 分布的 CPU microbenchmark + serving trace
RadixKey.match 或 _match_prefix_helpertest/registered/unit/mem_cache/test_radix_cache_unit.pyearly mismatch、late mismatch、exact hit 三种 prefix 分布

修改前先写自然语言等价性：输入 domain、输出、tree mutation、page alignment、extra_key 和 lock accounting 不变。然后保留相同 commit、硬件、seed、warmup、trace，报告 median 与 tail，不只报告最好一次。

验收标准

  • 能从函数入口追到 physical KV slot，不跳过 ownership transition。
  • 能手算至少两个 admission 与 page-alignment 例子。
  • 能为 tp/dp/ep 配置列出每个 collective 的 group。
  • 修改通过既有 correctness tests，并新增一个会在错误实现下失败的最小用例。
  • microbenchmark 有统计分布，端到端 benchmark 同时报告 TTFT、ITL、tok/s、retraction 与 cache hit。
  • 若端到端收益不成立，明确撤回 patch；不以局部 microbenchmark 代替产品结论。
材料完成不等于能力已验收只有你提交 trace、诊断与 benchmark 证据后，才能把本课程 mission 的最终能力写入 learning record。
