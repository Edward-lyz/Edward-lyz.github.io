Lesson 01: LLM 推理显存公式推导

从第一性原理到 MoE 模型 — 理解 aiak_ds_tool simulator 的显存计算核心

§1 核心问题

推理服务的核心约束：一张 GPU 卡能同时服务多少并发请求？

答案由显存决定。显存是固定的（如 H200 = 141GB），而占用显存的组成部分随 batch size 线性增长，所以存在一个 max_bs 上界。

max_bs = remaining_mem / (kv_per_token × layers × tokens_per_request)

其中:
remaining_mem = total_available - hold - weights - cuda_graph
tokens_per_request = ctx_len + output_len

这就是所有模型显存计算器的骨架。差异在于 weights 和 kv_per_token 的计算方式。

§2 显存的四大组成

组成部分是否随 BS 变化典型占比
① 模型权重❌ 固定40-70%
② KV Cache✅ 线性增长20-50%
③ CUDA Graph✅ 阶梯增长3-8%
④ 系统保留❌ 固定6-10%

2.1 可用显存基数

total_available = device.memory_size × 0.94

乘 0.94 是经验系数：CUDA runtime、driver、fragmentation 等不可控开销约占 6%。hold_mem（默认 3GB）进一步预留给 activation buffer、临时张量等。

2.2 模型权重（固定部分）

这是最复杂的部分，因 MoE 架构而产生特殊处理。

Dense 模型（Qwen3）

简单直接：权重总量固定，TP 分片后除以 tp_size。

weights = model_total_weights / tp_size

MoE 模型（DeepSeek V3/V4）

MoE 模型的权重分为两部分：

  • 非 MoE 权重：Attention（q_a, q_b, wkv, o_proj）、Norm、Embedding 等 — 每张卡完整持有
  • MoE 专家权重：按 EP（Expert Parallel）均匀分片到各卡
核心思路：用「实测单机单卡总权重」减去「该卡上 MoE 专家的 FP8 权重」，得到「非 MoE 权重」基准值。再根据实际 dtype 重新加回 MoE 部分。

推导过程（以 DeepSeek V3 为例）：

已知实测值：单机（8卡）target 模型，FP8 精度下，单卡显存占用 = 99GB

单个 expert 单层 FP8 权重 = inter_dim × hidden_dim × 3 / 1GB

= 2048 × 7168 × 3 / (1024³) ≈ 0.04101 GB

V3 总专家数 = 256，单机 8 卡 → 单卡专家数 = 32

V3 MoE 层数 = 58

∴ 非 MoE 权重 = 99 − 0.04101 × 58 × 32 ≈ 99 − 76.1 ≈ 22.9 GB

当 dtype 改变（如 fp4）时：

single_expert_layer = single_expert_layer_fp8 × moe_dtype_bytes expert_per_card = total_experts / (node_num × 8) target_weights = non_moe_weights + expert_per_card × single_expert_layer × moe_layers

V4 与 V3 的差异

参数V3V4

inter_dim20483072

V4 非 MoE 基准更大，因为 head_dim 从 128→512，加了 HC（Hybrid Connector）副本等。

2.3 KV Cache（BS 线性部分）

这是决定 max_bs 的关键弹性项。

标准 MHA/GQA（Qwen3）

kv_per_token_per_layer = kv_head_num × head_dim × 2 × dtype_bytes
// × 2 因为 K 和 V 各一份

MLA 架构（DeepSeek V3）

DeepSeek 使用 Multi-head Latent Attention，KV 被压缩到低维 latent space：

// 非 sparse 模式: 576 × 2 bytes/token/layer // sparse 模式: 771.2 bytes/token/layer (只存部分 head 的 KV) kv_per_token_per_layer = 576 × 2 / 1024³ // ≈ 1.07 × 10⁻⁶ GB

576 = latent_dim（c_kv_dim），乘 2 是 K 和 V。Sparse 模式下部分 head 用 RoPE 不压缩，额外开销使总量变为 771.2 bytes。

V4 的分层 KV Cache

V4 引入 compress_ratios，不同层有不同压缩方式：

层类型compress_ratiobytes/token/layer说明
SWA0~584NopeFp8RopeBf16Pack
C44~10244 倍压缩 KV + indexer
C128128~1024全压缩 KV
// V4 加权平均 KV Cache avg_kv = (swa_count × 584 + (c4_count + c128_count) × 1024) / total_layers

Hybrid Attention（MiniMax2.5）

只有 full_attn 层（62 层 GQA）产生 KV Cache，linear_attn 层不占 KV Cache：

// 只对 full_attn_layer_num 层计算 KV kv_total = kv_per_token × full_attn_layer_num × total_tokens

2.4 CUDA Graph 开销

CUDA Graph capture 会为每个 batch size 段录制一份执行图，占用固定显存：

graph_step = 8 // 每 8 个 BS 一个 graph graph_num = max_bs // graph_step graph_mem = graph_num × 0.176 GB // 每个 graph ≈ 180MB
CUDA Graph 显存形成循环依赖：graph_num 取决于 max_bs，而 max_bs 又受 graph_mem 影响。V1 解法：先不考虑 graph 算出初始 max_bs，用它估算 graph_mem，再扣除后重算。迭代一次即收敛。

2.5 MTP（Draft 模型）

Multi-Token Prediction 启用时，draft 模型的权重额外占用显存：

// Draft 模型只有 1 层 MoE draft_weights = draft_non_moe + expert_per_card × single_expert_layer × 1 // KV Cache 层数也要 +1（draft 层） kv_layers = main_layers + 1 // 61 + 1 = 62

§3 完整公式 — DeepSeek V3 为例

  1. 可用显存
    avail = device.memory_size × 0.94 − hold_mem
  2. 权重显存
    expert_fp8 = 2048 × 7168 × 3 / 1024³ non_moe = 99 − expert_fp8 × 58 × 32 expert_per_card = 256 / (node_num × 8) expert_actual = expert_fp8 × moe_dtype weights = non_moe + expert_per_card × expert_actual × 58 if mtp: weights += draft_weights
  3. 剩余显存
    remaining = avail − weights
  4. 初算 max_bs
    kv_layers = 61 + int(mtp) max_tokens = remaining / (kv_per_token_per_layer × kv_layers) max_bs_raw = max_tokens / (ctx_len + output_len)
  5. 扣除 CUDA Graph 后重算
    graph_mem = (max_bs_raw // 8) × 0.176 remaining -= graph_mem max_tokens = remaining / (kv_per_token_per_layer × kv_layers) max_bs = ceil(max_tokens / (ctx_len + output_len) / 8) × 8

§5 迁移到 V2 的设计考量

V2 的架构关键差异：

  • RuntimeContext 已包含 node_num、gpus_per_node、model_options
  • Strategy 体系可以 rewrite plan 和 compute_shape，但没有显存计算入口
  • ModelPlan 是纯拓扑结构，不含显存信息
  • V2 没有 memory_calculator 概念，需要新增

§6 自测

Q1: 为什么 V1 用「实测基准 - 专家权重」而不是直接按参数量计算非 MoE 权重？

因为非 MoE 部分包含 embedding、norm、lora adapter、projection 等多种小组件，逐一计算容易遗漏且难以精确。用实测总值反减已知的 MoE 部分，是更可靠的工程做法。代价是需要一个 FP8 精度下的实测基准值。

Q2: 为什么 CUDA Graph 的处理是「估算后扣除再重算」而不是解方程？

因为 graph_num = floor(max_bs / 8) 引入了取整运算，使得方程不连续，无法解析求解。但由于 graph 占比很小（通常 <5%），一次迭代就足够收敛。

Q3: MiniMax2.5 为什么不需要 CUDA Graph 扣除？

MiniMax2.5 的 calculator 是简化版本，可能实际部署中未使用 CUDA Graph 加速 decode（或其 graph 开销已被计入 hold_mem）。这是模型特定的工程决策，不是通用规则。
