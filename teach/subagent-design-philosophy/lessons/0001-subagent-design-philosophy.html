核心问题：为什么需要 Subagent

单个 LLM session 有三个天然瓶颈：

瓶颈表现Subagent 怎么解
Context 衰减对话越长，早期信息被 compaction 吞掉，判断力下降Fresh context child 从零开始审视，不受历史噪声干扰
角色冲突同一个 session 又要写代码又要 review，自我审查形同虚设Role isolation：writer 和 reviewer 是不同 session，互相对抗
串行瓶颈复杂任务只能一步步来，探索效率低Parallel fan-out：多个 scout/reviewer 并发跑
Subagent 的核心价值不是并发加速，而是 context isolation + role specialization。并发只是锦上添花。

两大流派对比

nicobailon/pi-subagents ⭐2222

设计哲学：Markdown-first 声明式角色

  • Agent 定义 = markdown frontmatter + system prompt
  • 内置 8 个角色（scout/researcher/planner/worker/reviewer/oracle/context-builder/delegate）
  • Prompt template 编排（/parallel-review, /review-loop）
  • Intercom 协议实现 child↔parent 通信
  • 重点：角色语义清晰，约束严格

tintinweb/pi-subagents ⭐482

设计哲学：Extension-first UI 驱动

  • 三工具模型：Agent / steer_subagent / get_subagent_result
  • 内置 3 个类型（general-purpose/Explore/Plan）
  • 运行时 widget（token 用量、compaction 次数、turn 进度）
  • Mid-run steering、worktree isolation、scheduled agents
  • 重点：可观测性 + 运行时控制
维度nicobailontintinweb
Agent 定义位置agents/*.md 独立目录.pi/agents/*.md
调用方式subagent({ role, task, ... }) 单工具Agent/steer/get_result 三工具

五角色模型

nicobailon 的 8 个内置 agent 可以归纳为 5 个核心职责。这个模型是 subagent 拓扑设计的基础：

Scout — 快速侦察，产出 context handoff
tools: read, grep, find, ls, bash(read-only)

目标：用最小 token 开销搞清楚代码结构。产出 context.md（关键文件 + 行号 + 架构）。thinking: low，追求速度不追求深度。

Planner — 产出可执行计划
tools: read, grep, find, ls, write（只写 plan.md）

目标：把 context + requirements 转化为编号步骤、文件列表、验证方式。不写代码，不做决策。thinking: high。

Worker — 唯一的写入线程
tools: read, grep, find, ls, bash, edit, write

目标：执行 plan 或 approved direction。遇到未批准的决策必须 escalate，不能自作主张。defaultContext: fork（继承上下文知道该做什么）。

Reviewer — 对抗性审查
tools: read, grep, find, ls, bash(read-only), edit(可选小修)

目标：从 fresh context 审视 diff，与 worker 形成对抗。关键约束：必须 fresh context，不能继承 worker 的认知偏差。

Oracle — 决策一致性守护
tools: read, grep, find, ls, bash(read-only)

目标：防止 context rot 导致的决策漂移。从 forked context 重建 baseline contract，检测当前轨迹是否偏离已批准方向。不写代码，不做新决策。

职责边界的核心原则：能写的不审，能审的不写。Worker 和 Reviewer 必须是不同 session，这是 subagent 存在的根本理由。

Context 传递策略

这是 subagent 设计中最关键的决策点。选错了，subagent 的价值归零。

策略含义适用场景风险
FreshChild 从空白开始，只有 system prompt + taskReview、audit、second opinion缺失关键上下文，可能重复已否决的方案
ForkChild 继承 parent 完整对话历史Worker 执行已讨论的方案、Oracle 检测漂移继承 parent 的认知偏差和 context rot
Selective传递 context.md / plan.md 等结构化 handoff跨阶段 pipeline（scout→planner→worker）handoff 可能遗漏隐含约束
Anti-pattern：Fork context 给 Reviewer。Reviewer 继承了 worker 的推理过程后，会不自觉地为 worker 的实现辩护而非挑战它。这就是为什么 nicobailon 的 /parallel-review 模板明确写死：Use fresh context, not forked context。
Golden rule：需要对抗 → fresh。需要延续 → fork。需要 handoff → selective（写结构化文件）。

nicobailon 的 context 过滤机制

Fork 不是简单的全量复制。Child 会过滤掉：

  • Parent 的 subagent tool-call/tool-result（避免 child 误以为自己是 orchestrator）
  • 旧的 orchestration 指令消息
  • Slash command / status 消息

保留：普通 prose、非 subagent 的 tool 调用和结果。这比全量 fork 更安全。

编排模式

Pattern 1: Parallel Fan-out（最常用）

Parent ├── Reviewer A (correctness) ─┐ ├── Reviewer B (tests) ─┼── 并发，fresh context └── Reviewer C (simplicity) ─┘ │ Parent synthesize → 决定哪些 fix 值得做 │ Worker (apply fixes) → fork context

关键设计：

  • 每个 reviewer 给不同 angle，避免重复劳动
  • 角度从 diff 内容动态生成，不是固定的三板斧
  • Parent 做 synthesis，不盲从任何一个 reviewer
  • 只做 fixes worth doing now，不做 optional improvements

Pattern 2: Review Loop（迭代收敛）

Worker (implement) │ ↓ ┌─ Reviewers (parallel, fresh) ─┐ │ 有 blocker? │ │ ├─ Yes → Worker (fix) ──────→│ (下一轮) │ └─ No → 结束 │ └─────────────────────────────────┘ max 3 rounds (防止无限循环)

停止条件（任一满足即停）：

  • Reviewer 无 blocker 且无 fixes worth doing
  • 剩余反馈全是 optional/speculative/deferred
  • Reviewer 发现未批准的架构决策 → 暂停问用户
  • 达到 max round cap

Pattern 3: Pipeline Chain（线性 handoff）

Scout (recon) → context.md → Planner (plan) → plan.md → Worker (implement) → Reviewer (verify)

每个阶段的产出是下一个阶段的输入。Selective context，文件即接口。

Pattern 4: Clarify → Plan → Execute（完整工作流）

Scout + Researcher (parallel recon) → context.md + research.md → Parent 向用户提问 (clarify) → Planner (plan) → Oracle (validate plan consistency) → Worker (implement) → Reviewers (parallel verify) → Worker (fix) → done

安全边界与隔离

Child 不能做什么

nicobailon 的关键安全设计：

  • Child 默认没有 subagent 工具 → 不能无限 spawn
  • Child 收到 boundary instruction：你不是 orchestrator，不能提议或运行 subagent
  • 只有 agent 定义中 tools 显式包含 subagent 的 child 才能 fan-out（受 maxSubagentDepth 限制）
  • Fork context 过滤掉 parent 的 subagent 历史 → child 不知道 parent 的编排细节

tintinweb 的隔离手段

机制作用
isolated: trueHermetic 模式：禁用 extensions + skills + context，只有 built-in tools
isolation: worktreeGit worktree 隔离：agent 在独立副本中编辑，完成后 auto-commit 到 branch
max_turns + grace防止 agent 失控：到 limit 后注入 wrap-up 指令，5 turn 内必须结束
disallowed_tools显式禁止特定 tool
Depth bomb 防护：如果 child 能无限 spawn child，token 成本指数爆炸。nicobailon 用 maxSubagentDepth 硬限制，tintinweb 用默认不注册 subagent 工具。两种方式等价有效。

设计决策清单

当你为自己的项目设计 subagent 拓扑时，按顺序回答这些问题：

#问题决策空间
1这个任务需要对抗性审查吗？需要 → 至少一个 fresh reviewer
2写入操作是否需要 guard？需要 → worker 必须有 escalation path
3任务能拆成独立子问题吗？能 → parallel fan-out
4需要外部信息吗？需要 → researcher 角色
5任务涉及架构决策吗？涉及 → oracle 做 drift check
6Parent context 是否已退化？退化 → 用 scout 重建，不要依赖 parent 记忆
7需要多轮收敛吗？需要 → review loop + max cap
8结果可逆吗？不可逆 → worktree isolation 或 dry-run

最小有效拓扑

日常小修改:    Worker (fork) → Reviewer (fresh) → done
中等 feature:  Scout → Planner → Worker → 3x Reviewer (parallel) → Worker fix
大型重构:      Scout + Researcher → Clarify → Planner → Oracle → Worker → Review Loop (max 3)
纯调研:        Researcher (parallel, 多角度) → Parent synthesize
奥卡姆剃刀应用于 subagent：能用一个 agent 解决的不要拆两个。每多一个 subagent 就多 N 万 token 的固定开销（system prompt + context loading）。只在瓶颈出现时才加 agent。

总结：三条第一性原理

  1. Context is king — subagent 的全部价值来自 context 管理。Fresh 用于对抗，Fork 用于延续，Selective 用于 handoff。选错 context 策略，subagent 就是浪费钱。
  2. 能写的不审，能审的不写 — 角色隔离不是形式主义。同一个 session 无法有效自我审查，这是 LLM 的认知局限，不是工程选择。
  3. Parent is the brain — 编排逻辑在 parent，不在 child。Child 只做分配给它的事。Synthesis 和决策权永远在 parent（最终在用户）。
